# Changelog

## [0.7.0]

### Added

- `@onebun/core`: a handler parameter with no param decorator is reported at startup, naming the controller, the handler and the 0-based index. What such a parameter receives depends on which dispatch arm the route lands in — a route with no decorated parameter and no response schema is called with the request, so the first parameter happens to be it, while on every other route the framework fills only decorated positions and an undecorated one is `undefined`. Adding a single `@Query()` therefore flipped the meaning of every other parameter on that handler, in both directions and in silence: a handler copy-pasted between two controllers worked in one and threw `Cannot read properties of undefined` in the other. The two dispatch arms are a measured optimisation and are unchanged; what is gone is the silence. `Function.length` stops counting at the first defaulted or rest parameter, so a gap after one of those is not reported — the message says what it can see rather than guessing. (WI-249)
- `@onebun/core`: exception filters can be registered as a CLASS and get constructor DI, like guards, middleware and interceptors already could. `@UseFilters`, `ApplicationOptions.filters` and the route metadata accepted instances only — passing a class was a compile error — and an instance was merged into the route untouched, so `this.logger`, `this.config` and anything the filter tried to inject were `undefined` inside `catch()`. That is the one place in an application that sees every unhandled error, and it was the only place that could not reach a service to report it to. `OneBunModule.resolveFilters()` now mirrors the interceptor resolver: one instance per class per module, constructor dependencies resolved from the owning module's scope, an unresolvable one failing the application at startup with the filter named, and an already-constructed instance passed through — initialized if it extends `BaseService`, so `this.logger` works there too. Constructor injection needs a class decorator (`@Service()`), the same rule interceptors have. (WI-266)
- `BaseWebSocketGateway.publishToRoom(room, event, data)` fans a message out to a room through Bun's native pub/sub — one call, fan-out in the runtime instead of a send per socket — on a topic scoped to the publishing gateway, so a room name used by two gateways does not collide. `getWsServer().publish(topic, …)` is deliberately unchanged: Bun's topics are a process-wide namespace and sockets stay subscribed to the raw room name as well, so existing `publish('lobby', …)` calls keep working exactly as they did. That path remains unfenced and is documented as such. Separately, a WebSocket storage adapter's `subscribe()` now returns a disposer that detaches only the caller's handler; `unsubscribe()` drops every handler on an adapter shared by every gateway in the application, so using it to detach one gateway silenced its siblings. (WI-371)
- `RedisClient.runScript(script, keys, args)` runs a Lua script server-side with the client's key prefix applied to every key. `raw('EVAL', …)` deliberately does not prefix, and a read-then-write pair issued as two commands is not indivisible. (WI-371)
- `websocket.storage: { type: 'redis', redis: { url, prefix } }` now does what it has always documented: WebSocket clients and rooms go to Redis and are shared by every instance, which is also what enables cross-instance `broadcast()` / `emitToRoom()`. The option was declared on `WebSocketApplicationOptions`, exported from `@onebun/core` and documented in three places, and read by no code at all — `WsHandler` built an in-memory adapter in its constructor before looking at any option. Measured against a real application with a live upgrade: the client sat in a `Map` and Redis held zero keys, so an operator who configured multi-instance ran single-instance and was told nothing. `prefix` reaches the connection, which is what owns the keyspace, so two applications on one Redis stay apart by setting different values. (WI-371)
  - Migration: `type: 'redis'` now makes Redis a startup dependency: a connection that cannot be opened fails `start()` instead of silently falling back to memory. Applications that already carry this option in their config were running in memory and will now genuinely use Redis — the state becomes fleet-shared and remote events start arriving.

### Changed

- Two unnamed `forRoot()` calls that disagree are now refused at `app.start()` instead of silently resolved by whichever ran last. A process that configures the same dynamic module twice without a token — different `isGlobal`, or a different configuration — makes every application that imports that module fail with `OneBunConflictingRegistrationError`, naming both call sites and pointing at `forRoot({ as: TOKEN })`. Previously the last call evaluated decided for the whole process: an application that wrote `isGlobal: false` could boot with ambient injection anyway, an application that declared nothing could fail to resolve a service it never opted out of, and two applications naming different databases both opened one of them. The check runs at boot and only for modules the booting application actually imports, so an unrelated application in the same process is unaffected, and two calls that agree stay silent. This is not per-application globality — that shape remains impossible, because `@Service()` mints one DI tag per class and an unnamed registration is identified by the module class itself. What changed is that the disagreement is now located instead of hidden. (BREAKING, WI-191)
  - Migration: If a process configures the same module twice without a token, give each configuration a name: `Module.forRoot({ ..., as: TOKEN })` where it is configured, and `Module.forFeature(TOKEN)` in the modules that need it. A named registration has its own module identity and its own options, and never touches the process-wide global registry. Test suites that configure one module several ways in a single run should call `resetRegistrations()` in `beforeEach` — the registry outlives the file, so a registration written by an earlier test, or by an earlier test file, is still in it. Applications with a single `forRoot()` per module are unaffected.
- `@onebun/core`: a request whose verb a declared path does not support now answers `405 Method Not Allowed` with an `Allow` header listing the verbs that path does declare, instead of the same 404 an unknown path gets — which sent developers hunting for a route that was right there. The remaining verbs are registered in the routes table, so Bun does the matching and `Allow` reflects exactly what the matched pattern declares, wildcards and params included. `HEAD` is answered from the matching `@Get` handler — same status, same headers, no body — unless the controller declares its own `@Head`, which wins; on Bun 1.4 HEAD already worked, and the derivation is what keeps it working now that the unclaimed verbs answer 405. When `cors` is configured the `OPTIONS` verb is left unclaimed, so the CORS preflight still answers on a routed path. The 405 travels the global middleware chain, so it carries the same security headers every other response does. (BREAKING, WI-281)
  - Migration: A request with a verb a declared path does not support now gets 405 instead of 404. Client code that treats 404 as "no such endpoint" will see 405 for the wrong-verb case — which is the distinction the change exists to make. Unknown paths still answer 404. If a route must accept every verb, that is what `@All()` is for.
- `@onebun/envs`: `TypedEnv.create(schema, options, key)` now throws when `key` is already bound to a structurally different schema, instead of returning the other schema's configuration. The `key` parameter keeps its meaning — one key is one configuration, and a repeated call with the same schema still returns the cached instance. (BREAKING, WI-291)
  - Migration: If you reused one `TypedEnv.create()` key for two different schemas, give each its own key — or drop the key entirely and let the schema identify the instance. Code that hit this was already running on the wrong configuration; the throw is the first time it says so.
- A WebSocket connection now belongs to exactly one gateway — the one whose path it connected to — and that gateway's handlers are the only ones that run for it. Before, the socket registry was a single process-wide `Map` and every event was fanned out over every registered gateway: measured, one client on a public `/chat` gateway fired BOTH gateways' `@OnConnect`, could invoke an `/admin` gateway's `@OnMessage('admin:secret')`, and received that gateway's `broadcast()` in its own inbox. Three narrowings follow. Reach: `broadcast`, `emit`, `clients`, `emitToRoom`/`emitToRooms`/`emitToRoomPattern`, `disconnectClient` and `disconnectAll` now cover only the connections that gateway admitted, in that application — two applications in one process no longer broadcast into each other's connections, and a gateway instance the framework never registered sees no clients at all. Dispatch: `@OnConnect`, `@OnMessage`, `@OnJoinRoom`, `@OnLeaveRoom` and `@OnDisconnect` run on the owning gateway only. Authentication: a Socket.IO client is bound to a gateway at upgrade, so that gateway's `authenticate` hook now runs for it — it did not before, because no gateway was resolved on that branch, and a hook returning `false` will refuse a Socket.IO connection that previously succeeded. `namespace` became functional rather than decorative: a client selects a gateway with `?namespace=<name>`, OneBun's own `WsClient` sends it when its `namespace` option is set, and a namespace matching no gateway is ignored rather than refused. Two gateway classes resolving to the same path (and namespace) now throw at registration instead of the second silently replacing the first and becoming unreachable. `_resetClientSocketsForTesting()` is a deprecated no-op: there is no process-wide map left to clear. (BREAKING, WI-303)
  - Migration: Code that relied on one gateway's `broadcast()` reaching another gateway's clients must send from the gateway that owns them — inject it, or give both a shared service. A gateway constructed by hand rather than registered in a module no longer sees live connections; use the instance the framework built. If two gateways share a path, give them different `namespace` values and have clients connect with `?namespace=<name>`, otherwise registration now throws. Applications using the Socket.IO protocol with a gateway that declares `authenticate`: that hook now runs for Socket.IO clients and can refuse them — verify it handles those clients before upgrading. With several gateways and the Socket.IO protocol, a client that states no namespace is bound to the first registered gateway and a warning is logged.
- `@onebun/core`: `app.getQueueService()` now returns `QueueService` and throws when there is none, instead of returning `null`. The explanation already existed — the injected proxy has always thrown a message naming the three ways to enable a queue — but the documented accessor bypassed it, so a producer-only application reaching for it got `TypeError: null is not an object (evaluating 'queue.publish')` on the next line. The thrown message now also distinguishes the three states it can be in: never enabled, still starting, already stopped. (BREAKING, WI-341)
  - Migration: `getQueueService()` no longer returns `null`. Code shaped like `const q = app.getQueueService(); if (!q) return;` now gets an exception instead of a falsy value — wrap the call in try/catch if a missing queue is a case you handle rather than a misconfiguration. Callers that used `!` or a cast are unaffected.
- `@onebun/core`: exception filters can decline, and the documented way to do it is real. Filters are now tried from the most specific outwards — route, then controller, then global, then the built-in default — and the first one to return a Response answers. Returning `undefined` declines and hands the error one level out. Only the most specific filter used to run at all, while the documentation showed `throw error; // pass to next filter`: there was no next filter, and a rethrow reached the DEFAULT filter, so the documented idiom for declining was indistinguishable from a bug in a filter. A throw is now treated as the bug it is — reported with the filter's class name and answered by the default filter, without consulting the rest of the chain — and a decline is a debug line. `ExceptionFilter.catch()` may return `undefined`; `createExceptionFilter()` is overloaded so a function that always answers still produces a filter that always answers. (BREAKING, WI-362)
  - Migration: If a filter of yours rethrows to "pass to next filter" as the documentation showed, replace `throw error` with `return undefined`. Rethrowing still falls back to the default filter, as it always did, but it is now logged as a filter bug with the class named. If several filters apply to one route, an outer one that never used to run may start running when an inner one declines.
- A Socket.IO client now picks its gateway with the namespace it states in the CONNECT packet, and `@OnConnect` runs when that packet arrives rather than at upgrade. The `nsp` field was parsed, echoed back and never consulted — it could not be, because the `@OnConnect` reply went out before the client sent it — so `io('/admin')`, which puts nothing in the query, was bound to whichever gateway happened to be registered first. The upgrade still binds provisionally (by `?namespace=`, the sole gateway, or the first with a warning) and still runs that gateway's `authenticate` hook; a bare `40` names no gateway and leaves that binding alone. OneBun's own `WsClient` now sends the CONNECT packet, carrying its `namespace` option. (BREAKING, WI-371)
  - Migration: A Socket.IO client that never sends a CONNECT packet no longer receives `@OnConnect` — every real Socket.IO client sends one, and OneBun's own client now does too. Switching namespaces to a gateway that declares `authenticate` is refused with a `connect_error`, because the hook gates the upgrade and there is no upgrade request left to run it against; reach that gateway with `?namespace=`.
- A pattern broadcast costs a round trip per matching room instead of per member. `emitToRoomPattern()` and `disconnectRoomPattern()` went through the gateway's fenced read path, which resolves every member's stored record to decide whether the ROOM is visible, and then fetched each room's member set a second time — in a multi-instance fleet most of those lookups were for clients the gateway could never send to anyway. Measured on 50 rooms of 20 members: 1151 commands for one broadcast, of which 1000 were per-member lookups. Both paths only ever reach sockets this gateway admitted, so the fence is unchanged. (WI-371)
- The Redis WebSocket storage no longer runs `KEYS` — `getAllRooms()`, `getAllClients()`, `getClientCount()` and `clear()` iterate with `SCAN` instead. `KEYS` walks the whole keyspace in one indivisible command: measured, a `PING` on a second connection during `KEYS ws:rooms:*` came back in 61 ms at a million keys, tracking the `KEYS` duration to within 0.04 ms, so every other client of that Redis was stalled for its full length. `SCAN` is slower in wall clock and that is the trade — the stall on everyone else drops to about 5 ms. `clear()` also deletes in batched `UNLINK` calls rather than one `DEL` per key (500 keys: 26.8 ms to 0.6 ms), and bulk reads fan out with a concurrency cap instead of one sequential round trip per item. (WI-371)
- Outgoing HTTP calls have their own metric family, their own destination and a bounded label. `createHttpClient` is a free function with no application, so it reached a process-wide slot — owned by whichever application started LAST — and recorded an OUTGOING call into the SERVER's own `http_requests_total` with `controller="requests-client"` and the full URL as the route. Measured: a call made by one application produced `beta_http_requests_total{controller="requests-client",route="http://127.0.0.1:35379/alpha/ping",app="beta"}`. Three consequences, all now fixed: a service's request rate counted the calls it MADE as well as the ones it served, and `sum by (controller)` grew a bucket that is not a controller; the series landed in the wrong application's registry; and the route label minted a fresh series for every path, every query string and every ephemeral port. Metrics now go to an explicit `metricsSink` in `RequestsOptions`, and `@onebun/metrics` exports `createRequestsMetricsSink(metricsService)` to build one. Calls are recorded as `<prefix>http_client_requests_total` and `<prefix>http_client_request_duration_seconds`, labelled `method`, `host` and `status_code`; both families are created on first use, so an application that never calls out exposes neither. (BREAKING, WI-372)
  - Migration: `metrics: true` alone no longer records anything — a client needs a sink: `createHttpClient({ metricsSink: createRequestsMetricsSink(metricsService) })`. The `controller="requests-client"` rows disappear; anything alerting or dashboarding on them moves to `http_client_requests_total`, where the per-endpoint breakdown is by `host` rather than by full URL. A client with no sink is silent rather than misattributed, which is the point: with no application to ask, guessing one was the defect.
- A gateway that was never registered with a `WsHandler` now says so once when it publishes: it has no key to stamp, and an instance running more than one gateway refuses a frame it cannot attribute, so those events reach nothing there. The three publish sites went through one helper so the notice cannot be added to two of them and forgotten on the third; a publish that rejects is now logged instead of becoming an unhandled rejection. (WI-373)
- Benchmarks page: every ratio and overhead figure in the prose is now computed from the same dataset the tables render, instead of being hardcoded. Stale claims that the latest CI runs contradicted are gone (the Honest Assessment block's ~2x/~4x/~1.7x numbers, "all frameworks land within noise" on uncached reads, "under 25% slower" observability cells, the ~477ms cold-start figure, and the "±20% between runs" variance note). Stack names in the prose now match the table rows, and the offline fallback dataset was refreshed to the latest CI run. (WI-58)

### Fixed

- Two applications in one process that configure the same dynamic module with an unnamed `forRoot()` no longer end up sharing one target. Measured before: two services, both plain `DrizzleModule.forRoot()`, one naming `db_a.sqlite` and one `db_b.sqlite` — both opened `db_b.sqlite`, and `db_a.sqlite` was never created, because the unnamed registration record is keyed by the module class and the second call replaced the first with no duplicate check. The disagreement is now refused at `app.start()`, before any connection is opened, by the same check that refuses a globality disagreement. Configurations that must coexist take a token: `forRoot({ as: TOKEN })` with `forFeature(TOKEN)`. Note the class-static options slot is unchanged — `Module.getOptions()` is still last-writer-wins for services built by hand with no module, and `clearOptions()` is still its reset. (WI-243)
- `DependencyResolutionError` no longer sends developers to a module that merely has a same-named class. The suggestion builder compared class NAMES across a process-wide map of every `@Module()` evaluated anywhere, including packages the application never imports — so a missing `MailerService` produced `MailerService is exported from ThirdPartyMailModule. Add ThirdPartyMailModule to imports of AppModule.`, naming a different class in a package nobody used. That was the only line the developer got, because the correct advice ("decorate it with `@Service()` and list it in a module's providers") prints only when nothing else matched, and the false hit filled the list. Matching is now by class identity. Two further messages are corrected: a module that is `@Global()` but was never imported by this application no longer reports "it should be auto-resolved, check module initialization order" — nothing constructed it, so the message now says a `@Global()` module still has to be imported once; and a service provided by a named registration is no longer reported as "Add CacheModule_fragments to imports", a minted class name that exists nowhere in the user's source, but as an instruction to import `CacheModule.forFeature(<token>)`. (WI-246)
- `forRoot({ as: TOKEN, isGlobal: false })` no longer switches off ambient resolution for the module's UNNAMED registration. The global-module registry is keyed by the module class and shared by the whole process, and a named call was writing to it: measured, `isGlobalModule(CacheModule)` went from `true` to `false` across a named `forRoot()`, and an unrelated module that injected `CacheService` without importing anything then failed to boot — with the error naming that innocent module rather than the call responsible. Only an unnamed `forRoot()` decides the base module's globality now. `isGlobal: false` alongside `as` is accepted and does nothing, because a named registration is never ambient to begin with; `isGlobal: true` alongside `as` still throws, because that one asks for something impossible. Both spellings are documented, and the JSDoc on `isGlobal` says it is ignored when `as` is given. (WI-248)
- `@onebun/core`: `QueueService.publish()` now works from `onModuleInit` and `onModuleDestroy`. Both ends were broken for the ordinary "announce this instance on boot and on shutdown" pattern. On boot the injected proxy had no delegate yet — the real service is created after the module tree is set up — so the call threw "Queue is not enabled" and, uncaught, took `app.start()` down with it; the error listed three ways to enable a queue that was already enabled. A publish issued while the queue is starting is now held and sent once the handlers are registered, so a subscriber declared in the same application receives it, and the call answers immediately with the real message id (`options.messageId` is honoured by every adapter). On shutdown the queue was torn down before `onModuleDestroy` ran, so the goodbye message threw into a caught hook error while `stop()` still reported a clean shutdown; consumers and the scheduler are still stopped first, but the transport now closes after the destroy hooks. The two other unavailable states got their own messages instead of sharing the enablement one: "still starting" names what to wait for, "stopped" names the shutdown. (WI-250)
- Each application now owns its own Prometheus registry, so metrics work in a process that runs more than one — which is what multi-service mode is. Before, everything went into prom-client's process-global registry and it failed two different ways. With the default prefix, the second application's `collectDefaultMetrics()` threw on a duplicate metric name; the throw was swallowed, its metrics service was never built, and its `/metrics` answered 404 — while `setDefaultLabels` had already run, so the FIRST application's series came out stamped with the SECOND one's identity (`onebun_http_requests_total{route="/users/ping",service="orders"}`). With a distinct `metrics.prefix` per service, which is what the multi-service page recommends, there was no error and both endpoints served everything: a Prometheus job scraping both targets double-counted every series in the process. A scrape now returns only the scraped service's series, with its own `defaultLabels`. `this.metrics` inside a service or controller resolves that application's service rather than a process-wide slot the last application to start overwrote, so a custom counter created in one service no longer lands in another's registry. Stopping an application releases its registry and the slot. Two related diagnostics: a metrics service that fails to construct now says so at ERROR with its stack instead of at DEBUG, and the startup summary no longer tells the operator to install `@onebun/metrics` when the package is installed and threw. Process-level series (CPU, memory, event loop) describe the process and are therefore exposed by every service — aggregate them with `max`, not `sum`. Still outstanding, and documented rather than implied: `@Timed()`, `@Counted()`, `@Gauged()` and `WithMetrics()` used as a method decorator resolve the metrics service through a process-wide slot, because a method decorator runs at class-definition time with no application to ask; in a multi-service process they attach to whichever service started last. (BREAKING, WI-251)
  - Migration: A metric built as `new Counter({ ..., registers: [register] })` against the `register` re-exported from `@onebun/metrics` still registers, but no application serves it. The framework names such metrics once, on the first scrape, in a WARN. Two supported routes: build them through the service — `this.metrics.createCounter({ name, help })` inside a service or controller, or `metricsService.createCounter(...)` — or opt one application back onto the global registry with `metrics: { registry: register }`, which restores the previous behaviour verbatim. `Registry` is now re-exported from `@onebun/metrics` so that option is constructible without a direct prom-client dependency. To read an application's registry directly, use `metricsService.getRegistry().register`; the `register` export is deprecated and still points at prom-client's process-global registry, which is no longer what any application scrapes.
- `@onebun/core`: static files and unmatched paths now go through the global middleware chain. Global middleware was merged into per-route handlers only, so everything the `Bun.serve` fallback answered was a bare Response: with `security: true` a served SPA carried no CSP and no `X-Frame-Options` — the whole reason to serve it from the API origin — and `rateLimit` bounded only the paths that happened to match a controller, so an attacker hammering nonexistent ones was entirely unmetered. Both now carry the same header set a matched route does, and both consume rate-limit budget. Two things stay outside the chain deliberately: the CORS preflight short-circuit, which answers with CORS headers alone and must not be seen by rate limiting or auth, and a WebSocket upgrade, which hands the socket to Bun rather than producing a response. The per-route chain and the fallback now run through one implementation rather than two. (BREAKING, WI-259)
  - Migration: `rateLimit.max` now bounds every request, not only the ones that match a controller route: static assets and unmatched paths consume budget. A page that pulls 30 assets spends 30 of the budget, so raise `max` or serve assets from a CDN. If you relied on 404s being free, they are not any more — that was the defect.
- `@onebun/core`: a cron expression that restricts both the day-of-month and the day-of-week field now matches when EITHER field matches, as crontab(5) specifies. It required both, so a line copied straight out of a crontab silently lost most of its runs — `0 0 1 * 1` means "the 1st of the month or any Monday" and fired only when the 1st fell on a Monday, about once a year instead of about 57 times. Nothing reported it: the job registered, and `nextRun` showed a plausible date. Expressions restricting only one day field are unchanged, and a leading `*` still counts as unrestricted even with a step, so `*/2` in the day-of-week field does not switch the pair into OR mode. `CronSchedule` gained `daysOfMonthRestricted` and `daysOfWeekRestricted` — the value arrays could not carry the difference, since `*` and `1-31` parse to the same 31 numbers. Both are optional, so a hand-built schedule still compiles; when absent, the rule is inferred from whether the array names every day. (BREAKING, WI-260)
  - Migration: Any `@Cron` expression that restricts BOTH the day-of-month and the day-of-week field now fires on many more days — it was firing on the rare intersection. Check every such expression before deploying: `0 0 1 * 1` used to run about once a year and now runs on the 1st of each month plus every Monday. Expressions with a `*` in either day field are unaffected, which is nearly all of them. If you split a schedule into two `@Cron` methods to work around this, collapse them back into one or they will now double-fire.
- `@onebun/core`: on the in-memory adapter, a delayed message with a higher priority no longer holds back messages that are already due. The delayed buffer was sorted priority-first and drained from the head only, so `publish(..., { delay: 3600000, priority: 10 })` parked itself at index 0 and withheld a `{ delay: 60000, priority: 1 }` message for the full hour — a steady trickle of such messages withheld it indefinitely. The adapter advertises both `delayed-messages` and `priority`, and combining them was the failure. `delay` now decides when a message becomes deliverable and `priority` decides only the order among messages that came due in the same pass; every due message is dispatched, not just the ones ahead of the first that is not. (WI-267)
- `@onebun/core`: a cron expression that parses but can never match — `'0 0 30 2 *'`, February 30th — is now refused at registration instead of being stored as a job that never fires. It used to register silently: the job appeared in `getJobs()`, unpaused, with no `nextRun`, and the tick skipped it on every pass forever, so a typo in a schedule surfaced only when someone noticed the report or the cleanup had not run. `addCronJob()` and `updateJob()` throw, naming the job and the expression; a failed `updateJob()` leaves the job on the schedule it already had. A job that loses its next run while the application is live — through `resumeJob()` or a tick — is reported through the scheduler's error handler, which the application logs, once rather than on every tick. (BREAKING, WI-271)
  - Migration: An application carrying a cron expression that can never match now fails to start instead of running with an inert job. If a deploy stops booting on this, the job it names was never firing — fix the expression or remove the job. `updateJob()` on such an expression now throws too, and leaves the job on its previous schedule.
- `@onebun/core`: an HTTP interceptor now sees a handler error. Exception filters were applied inside the two handler arms, below the interceptor chain, so by the time `next()` returned the throw had already become a Response and `try { await next() } catch` was dead code — an error-counting interceptor counted only successes. The same class attached to a `@Subscribe` handler or a WebSocket handler saw the throw, because those transports have no filter layer: one interceptor, three transports, two behaviours. Filtering moved to a single boundary that wraps the interceptor chain, so the throw reaches the interceptor and the filters answer once it rethrows. The boundary stays below the middleware chain, so CORS and security headers set after `await next()` are still on error responses. It also covers parameter extraction and schema validation, which sit inside the same handler call — a deliberate widening: an interceptor measuring failures should count a 400. (BREAKING, WI-279)
  - Migration: An HTTP interceptor with `try { await next() } catch` now enters that catch block on a handler error, where it used to receive a finished error Response. If your interceptor swallows what it catches, it will start swallowing handler errors too — rethrow to keep the filtered response. An interceptor also now sees errors from parameter extraction and schema validation, so a metrics interceptor counting failures will include 400s it did not count before.
- `@onebun/core`: registering a scheduled job under a name that is already taken now throws instead of replacing the existing one. Job names are one flat namespace and default to the bare method name, so two controllers each with a `cleanup()` method collided: the second registration replaced the first in the scheduler's map, and the lost schedule was never reported at any log level. For `@Interval` and `@Timeout` it was worse than a lost job — the replaced job object kept a live timer that the map no longer referenced, so neither `stop()` nor `removeJob()` could clear it and the process kept publishing after `app.stop()`. The error names both jobs, both patterns and the remedy. (BREAKING, WI-284)
  - Migration: An application with two scheduled handlers resolving to the same job name now fails to start, naming both patterns. That application was already losing one of the two schedules silently — give one of them an explicit `name` in its `@Cron` / `@Interval` / `@Timeout` options.
- `@onebun/envs`: `TypedEnv.create()` no longer caches every configuration in one process-wide slot. Instances are now keyed by the schema object and the options that shape the load, so a second schema in a process gets its own configuration instead of the first one's. This is what made per-service `envOverrides` and `envSchemaExtend` dead for every multi-service service after the first, and made a library shipping its own env schema alongside an application silently inherit whichever ran first. (WI-291)
- `@onebun/core`: an interceptor class is now constructed once per application, not once per registration site. `resolveInterceptors` ran inside the per-route loop and constructed unconditionally, so a class covering three routes became three instances — each route permanently bound to its own — and a global interceptor got one instance per route in the application. Any state the interceptor kept was therefore per route without saying so: a rate limiter set to 100 allowed 100×N, and a constructor that opened a client or built a lookup table paid for it N times at boot. `BaseInterceptor`'s own documentation had always promised the opposite ("instantiated once at application startup and reused for every matching request/message"). The cache sits in the shared resolver, so WebSocket handlers and queue subscriptions — which resolve per handler and per subscription — are fixed by the same change, and one class used across all three transports is one instance. Passing an instance instead of a class is unchanged: the caller owns its lifetime, and two instances of one class stay two. (WI-293)
- `@onebun/core`: middleware and interceptor classes now receive the module lifecycle hooks on the instance that actually serves requests. Every lifecycle pass walked only `serviceInstances` and `controllerInstances`, and pipeline elements are built elsewhere, so `onModuleInit` never ran on them: a middleware that opened a pool in the hook served its first request with the field still unset. Registering the class in `providers` made it worse rather than better — that produced a second instance which got the hook and never saw a request. `onModuleInit` runs in a pass of its own, after routes are registered and before the server accepts anything, because that is when those instances exist; `onApplicationInit`, `onModuleDestroy` and `onApplicationDestroy` were added to the passes that already existed, with pipeline elements destroyed first since they are constructed last. Guards are deliberately excluded: they are constructed per request, so there is no single instance a hook could belong to, and a guard class implementing `onModuleInit` is now reported once at startup instead of being skipped in silence. (WI-295)
- `@onebun/core`: a class registered in a module's `providers` that carries `@Subscribe`, `@Cron`, `@Interval` or `@Timeout` is now reported at startup instead of being skipped in silence. Handler discovery walks controllers only — that rule is unchanged and documented — but nothing enforced it, so the decorators were metadata nothing read: no handler ran, no error appeared, and the one debug line such an application printed said "no handlers detected" three lines below a handler the user had just written. Startup now emits one warning per offending class naming the class and every decorated method, and when those are the only handlers in the application the disabled-queue debug line says the decorators are on providers rather than claiming none exist. Both reports fire before the enablement decision, so the application that most needs to hear it — the one whose queue therefore never starts — is the one that does. (WI-301)
- `@onebun/core`: a `Response` built by the handler now reaches the client exactly as built, on every route. Routes with no decorated parameters already did; one `@Param`, `@Body`, `@Query` or even `@Req` moved the route to the other arm, which cloned the response, read it to text, `JSON.parse`d it and rebuilt it with `JSON.stringify`. Two consequences, both silent and both 200 OK: a 64-bit identifier sent as a JSON number came back rounded (`12345678901234567890` → `12345678901234567000`), and a streaming body was buffered whole, so a client saw nothing until the producer finished — measured at 401 ms versus 3 ms on the same handler without the decorated parameter. The round trip existed to let `@ApiResponse` validate the body, and that is now skipped for a handler-built `Response`: reading the body is what caused both defects, and a stream has no body to read without ending it. The schema still documents the endpoint, and the framework logs once per route that it is not validating one. (BREAKING, WI-305)
  - Migration: If a route both returns a `Response` and declares an `@ApiResponse` schema, the schema no longer reshapes that body — undeclared fields are no longer stripped and the response is not re-serialized. The framework logs which routes those are, once each. Return a plain object instead of a `Response` if you want the schema enforced at runtime; the schema documents the endpoint either way.
- `@onebun/core`: two guard defects. The four composite guards — `MessageAllGuards`, `MessageAnyGuard`, `WsAllGuards`, `WsAnyGuard` — were the only built-in guards with no transport check: they handed whatever context they were given straight to their children, so a composite of built-ins denied on the wrong transport by accident, and one with a hand-written child threw a `TypeError` inside `canActivate` instead of denying — on HTTP that reached the exception filter as a 500, a fail-open shape for something whose job is to fail closed. They now narrow first, like every leaf guard. Second, guard merging is deduplicated by identity on every transport, not only on WebSocket: a guard named on both a controller and one of its routes, on both a class and its method, or under both `@UseGuards` and `@UseMessageGuards`, now runs once per request or message instead of twice — doubled database work and doubled denial log lines, on a decision that is only idempotent if the guard happens to be. (WI-328)
- `@onebun/core`: `ApplicationOptions.interceptors` now applies to every transport, not only HTTP. The list was merged at HTTP route registration and nowhere else, so a global logging, metrics or tracing interceptor covered HTTP routes and silently skipped every WebSocket message handler and every `@Subscribe` subscriber — no warning at startup, nothing in the logs, and the gap invisible until a transport went missing from a dashboard. The option is named and typed as an application-wide setting, and it now behaves like one: the global list wraps outermost on all three transports, ahead of gateway-level and class-level lists, which is the order HTTP routes already used. Scheduled handlers (`@Cron`, `@Interval`, `@Timeout`) remain unwrapped — that is WI-320. (BREAKING, WI-329)
  - Migration: A global interceptor now also wraps WebSocket message handlers and `@Subscribe` subscribers. If yours assumes an HTTP context — reading `ctx.getRequest()` without checking the transport — guard it with `isHttpContext(ctx)` before it runs against a message it was never given before.
- `@Timed()`, `@Counted()`, `@Gauged()` and `WithMetrics()` now record into the application that built the instance the method runs on, instead of whichever application started last. A method decorator is applied at class-definition time, before any application exists, so these resolved the metrics service through a process-wide slot. Measured with two applications: a `@Timed()` method belonging to the FIRST produced `beta_AlphaService_timedWork_duration_*{app="beta"}` — wrong prefix, wrong identity, served from the wrong endpoint, and since the decorator creates a metric on first use, CREATED in the wrong registry, so the second application permanently owned a series describing work it never did. The first application's `/metrics` contained no trace of its own decorated methods. The framework now stamps every instance it constructs — services, controllers, gateways, middleware, interceptors, filters and guards — with the scope of the application that built it, and the decorators read that stamp off `this` at call time. The service is dereferenced per call rather than captured, so an instance of a stopped application records nothing instead of writing into a disposed registry. An instance the framework did not build (a plain class, a static method, a detached function reference) still falls back to the process-wide slot, exactly as before; in a single-application process the two are the same service. `BaseMiddleware`, `BaseInterceptor` and `BaseWebSocketGateway` also receive their application's scope now, which makes `this.metrics` correct inside them and not only inside services and controllers. (WI-366)
- `SharedRedisProvider.configure()` refuses a second configuration that asks for a different target instead of accepting it and changing nothing. There is one shared connection per process, so a second call naming a different `url`, `keyPrefix`, `reconnect` or `tls` now throws `OneBunSharedRedisConflictError` naming both targets and both call sites. Before, the assignment was unconditional and the live connection kept serving the first target: two applications that believed they were on different Redis databases were on one, under the first one's key prefix — so one application's `clear()` reached the other's data, and nothing said so at any point. Passwords are masked in the message. Re-stating the same configuration is still fine, and `reset()` gives the configuration up. (BREAKING, WI-367)
  - Migration: A process that genuinely needs two Redis targets should use a dedicated client for the second — `SharedRedisProvider.createClient({ url })`, or the consumer's own connection options (`createRedisCache({ url })`, the queue adapter's `redis.url`) — rather than reconfiguring the shared provider. Test suites that point the provider at several containers in one run need `await SharedRedisProvider.reset()` between configurations; the save-and-restore pattern (`getOptions()` then `configure(saved)`) keeps working because restoring the same object is not a conflict.
- A gateway can no longer read another gateway's rooms and clients, and a remote WebSocket event reaches only the gateway that published it. Binding a connection to one gateway fenced what a gateway SENDS; it did not fence what a gateway READS, and room storage is shared by every gateway in an application. Measured: `getRoom('zone:admin')` called on a `/chat` gateway returned the admin gateway's room with its exact membership; `getRoomsByPattern('zone:*')` listed both gateways' rooms; and `getClientsByRoom` / `getClient` handed back the FULL record of a foreign client — `auth`, `metadata` and the key naming its owner. `getClient`, `getRoom`, `getClientsByRoom` and `getRoomsByPattern` now answer only about connections this gateway admitted, and `emitToRoomPattern`/`disconnectRoomPattern` inherit that because they enumerate through it. `joinRoom`/`leaveRoom` gained the matching write fence: the storage half used to run unconditionally while only the socket subscription was fenced, so one gateway could enrol another's client into a room — a membership neither gateway could then see. With the Redis adapter, the subscriber filtered on `sourceInstanceId` alone, which is minted per GATEWAY rather than per process: a publish looped back through Redis and the SIBLING gateway in the same process replayed it to its own clients, re-opening the boundary that had just been closed. Published payloads now carry the publishing gateway's key; a payload without one (an instance running an older build) is still delivered, and the receiving gateway warns once. Separately, `RedisWsStorage.subscribe` raised its `subscribed` flag AFTER the await, so concurrently-initialising gateways each installed a Redis-level listener that iterated the shared handler list — measured, two gateways delivered every remote message FOUR times to every client, three would deliver nine. The subscription is now memoised. `get rooms()` returns this gateway's actual rooms instead of an empty Map, and no longer points at a `getRoomsAsync()` that was never written. (BREAKING, WI-369)
  - Migration: Code that used one gateway to inspect another's rooms or clients — a monitoring gateway reading `getRoomsByPattern('*')`, for instance — now sees only its own. Register such code as part of the gateway that owns the connections, or hold the storage adapter directly. Room NAMES are unchanged and no Redis key moved: this is a read filter, not a repartition, so two gateways may still use the same room name and simply not see each other in it. `getWsServer().publish(topic, …)` remains unfenced — Bun's native pub/sub topics are the raw room names shared by the whole process; use `emitToRoom()` unless that reach is what you want.
- Whoever takes a hold on the shared Redis client now gives it back, and an application releases nothing. The count was not an ownership record: acquisition was per CONSUMER — a cache, a queue adapter — while release was one per APPLICATION, in `stop()`, gated on the client being connected rather than on that application having acquired anything. Measured against a live Redis, it broke in both directions. An application with no Redis at all took a sibling's hold to zero on its own shutdown and disconnected the client the sibling was using: the sibling's next queue publish threw `Redis client not connected. Call connect() first.` And an application whose cache AND queue both used the shared client took two holds and gave back one, so the socket outlived every application in the process. The cache now releases its hold in `close()`, the Redis queue adapter in `disconnect()`, the Effect layer in the finalizer that was an empty body, and code that called `SharedRedisProvider.getClient()` releases with `SharedRedisProvider.release()`. Four smaller defects fell out of the same change and are fixed with it: a failed acquire no longer leaves a hold behind (the count was incremented before the configuration check, so an unconfigured provider or a refused dial stranded one); `release()` with nothing outstanding no longer force-closes a client another consumer just acquired; `reacquire()` no longer restores the count by assignment, which swallowed a concurrent acquire; and `disconnect()` voids outstanding holds by identity, so a later release from a voided holder cannot take the connection away from whoever acquired after it. New: `SharedRedisProvider.acquire(label)` returns a handle whose `release()` is idempotent — prefer it to `getClient()`. `stop({ closeSharedRedis })` is deprecated and ignored, warned about once per process. (BREAKING, WI-370)
  - Migration: Code that called `SharedRedisProvider.getClient()` and relied on `app.stop()` to clean up must now release its own hold: `await SharedRedisProvider.release()` on shutdown, as `docs/api/security.md` already instructed. Without it the socket stays open and the process does not exit — the shutdown log names the holder and its call site at debug level (`Shared Redis still held by 1: your-file.ts:41`). Prefer the new `const lease = await SharedRedisProvider.acquire('my-consumer')` / `await lease.release()`, whose handle is harder to forget than a static call. `stop({ closeSharedRedis: false })` no longer keeps the connection open — it never needed to, since an application no longer closes it; remove the option, it is ignored and warns once. Applications that use the framework's own cache or Redis queue need no changes: those consumers release their own holds.
- A WebSocket instance that dies without running its shutdown path no longer leaks its Redis state forever. No key had a TTL and nothing recorded which instance owned which client, so a crashed pod left its `ws:clients:*`, `ws:rooms:*`, `ws:room:members:*` and `ws:client:rooms:*` entries in place — measured, a fresh instance on the same Redis then reported those dead sockets in `getClientCount()`, listed them as room members, and handed out their full records with the original `connectedAt`. Each instance now keeps a liveness key with a 30-second TTL refreshed every 10 seconds, plus an index of the clients it admitted; the next instance to take a connection reaps the clients of any instance whose key has expired, through the ordinary `removeClient()` path so rooms are cleaned with them. The liveness is per instance rather than per client on purpose: native connections have no per-connection heartbeat, so a TTL on client keys would evict live sessions — measured, one second into a native client's session. (WI-371)
- A WebSocket upgrade now goes to the gateway whose declared `path` covers it most specifically, and a path prefix has to end on a segment boundary. Resolution was a raw `startsWith` that returned on the first hit in registration order, so `/chat` claimed `/chatterbox`, and with `/chat` and `/chat/admin` both declared a request below both went to whichever was registered first — declaration order decided routing. `/` is unchanged and still covers every path: it is what `@WebSocketGateway()` defaults to, so an application that declares no path keeps accepting clients on any URL. (BREAKING, WI-371)
  - Migration: A connection whose path only shares a prefix with a gateway mid-segment (`/chatterbox` against a `/chat` gateway) is now answered 404 unless some gateway declares `/`. If an application leaned on that, declare the path it actually serves — or a `/` gateway to keep the catch-all.
- The Redis WebSocket storage keeps room membership in one place instead of two, and a join or a leave is now a single indivisible step. Membership was recorded both in the `ws:client:rooms:<id>` set and mirrored into the client record that `WsRoomGuard` reads, by an unguarded read-modify-write — so `deleteRoom()` cleaned the set and left the mirror granting access to a room that no longer existed, and three joins in one tick left the mirror holding one of them. Join and leave each ran over several round trips, and the gaps were windows: measured, a join landing three round trips into a concurrent leave had its membership deleted, and a room could end up with members but no record, invisible to `getAllRooms()` and to pattern broadcasts. (WI-371)
- WebSocket room membership now reads back the same through either storage adapter. `gateway.joinRoom()` never wrote to `ws.data.rooms` — the field `WsRoomGuard` reads and `gateway.rooms` is built from — and only appeared to work in memory mode, where the stored client record still shared the live socket's `rooms` array. Under Redis nothing was shared, so `joinRoom()` populated storage and the guard went on denying the client. In memory the reverse held on the way out: `leaveRoom()` emptied storage but left the room in `ws.data.rooms`, so a client removed from a room kept passing `WsRoomGuard` for it until it disconnected. Both halves are now maintained explicitly by the gateway. (WI-371)
- WebSocket shutdown removes only the clients that instance was serving. It called `storage.clear()`, which under the Redis adapter globs the whole key prefix — so one pod shutting down cleanly deleted every other pod's live clients and emptied their shared rooms, and a rolling deploy blanked the survivors on every replica it cycled. (WI-371)
- `InMemoryWsStorage` hands out records that share nothing mutable with the caller. Its shallow copies kept the caller's `rooms` array, `metadata` and `auth`, so a caller could write into storage it had only read from, and storage could write into a live socket. Optional keys stay absent rather than being materialised as `{}`. (WI-371)

### Security

- A WebSocket pub/sub payload or client record that names no gateway is now refused, unless the application registered exactly one gateway. Both readers used to accept anything unkeyed so that an instance running a build from before the gateway key stayed interoperable through a rolling deploy — but accepting is precisely the cross-gateway leak the key was added to close: measured, one unkeyed frame arriving at a two-gateway instance was delivered to both `/chat` and `/admin`, and an unkeyed record was visible through every fenced read of every gateway. With a single gateway there is nothing to be confused with, so that case is kept and a rolling deploy still works; with more than one the frame or record cannot be attributed and is refused, with a one-time log line saying so. This is the rule the upgrade path already applied — a connection whose gateway cannot be established is refused rather than guessed at. (WI-373)
  - Migration: Affects only an instance sharing one Redis with an instance running @onebun/core 0.6.0 or earlier that reached the Redis WebSocket storage by hand (`wsHandler.setStorage(createRedisWsStorage(client))` — the `websocket.storage` option did nothing in those versions). If that instance's application has more than one gateway, its events stop reaching the new instance and its clients become invisible to it; events published the other way are unaffected. Single-gateway applications are unchanged.

### Read This First

Ten entries below are breaking, three of them security-relevant. Two stop an application from
booting, and that is the fix in both cases — each was previously a silence. Each entry carries its
own **Migration** note where it appears; this is the index.

- **`auth: { type: 'onebun' }` authenticated nothing** — it verified a payload rebuilt from two
  headers no client ever sent, so only a literal `GET /` could validate and every request worth
  protecting failed open. The scheme is rewritten and the wire format changed: **both ends must
  upgrade together**, and `validateOneBunAuth` is removed rather than deprecated.
- **`auth: { type: 'apikey', location: 'query' }` never reached the wire** — the URL was built
  before auth ran, so those calls went out with no key at all. They start carrying one now, which
  means the key starts appearing in the callee's access logs.
- **The 500 body no longer carries the error's message or its stack** — for any unhandled throw
  both were echoed verbatim, disclosing paths, hosts and credentials to whoever could provoke a
  500. `exposeErrorDetails: true` returns the old body; the stack was always in the logs.
- **`json`/`jsonb` columns were stored double-encoded on PostgreSQL** — every value written
  through `DrizzleService` landed as a jsonb *string*, so `jsonb_typeof` answered `string` and no
  operator or index worked. **The on-disk format changes**: existing rows need migrating.
- **`RedisCache.clear()` could delete outside its own keyspace** — with an empty key prefix it
  issued `KEYS *` and a `DEL` per hit, so one "flush the cache" call destroyed every other tenant
  of that Redis database.
- **`pool.*` was accepted and then discarded** on PostgreSQL — every pool option an operator
  configured was read and thrown away. `pool.min` is removed rather than made to work.
- **`queue.redis` now selects the Redis adapter**, where it used to only enable the queue. An
  application with a `redis` block and no `adapter` was silently running an in-memory queue whose
  messages never left the process; it now connects, and **fails to boot if Redis is unreachable**.
- **A JetStream subscription no declared stream binds is refused at startup** — it used to be
  bound to whichever stream was declared first, where it received nothing forever, with
  `isConnected()` reporting true. **Some applications will stop booting**; the migration note has
  an offline check to find them before you upgrade.
- **A `keyPrefix` alongside `useSharedClient: true` is rejected** rather than silently discarded.
  If you passed both, your keys were never under the prefix you asked for.
- **`Message.params` is a required field** on `Message<T>` — code that constructs a message by
  hand (test doubles, custom adapters) must add it. `params: {}` is correct where there was no
  pattern capture.

### Added

- **`createPostgresContainer()` in `@onebun/core/testing`**, alongside `createRedisContainer` and `createNatsContainer`. ```typescript import { createPostgresContainer, type TestContainer } from '@onebun/core/testing'; let postgres: TestContainer; beforeAll(async () => { postgres = await createPostgresContainer(); // postgres.url → 'postgresql://onebun:onebun@localhost:55231/onebun_test' }); afterAll(async () => { await postgres.stop(); }); ``` Same shape as its two siblings — `url`, `host`, `port`, `container`, `stop()` — with `database`, `username` and `password` options on top of `image` and `startupTimeout`. Default image `postgres:16-alpine`. It waits for the **second** `database system is ready to accept connections` line, which is not a typo: the postgres image starts a temporary server to run its initialisation scripts, logs that line for it, shuts it down and only then starts the real one. Waiting for the first hands back a URL that is about to stop working, and the failure lands in whichever test connects first rather than in the helper. There was no PostgreSQL integration-test infrastructure at all before this, which is the direct reason a silent jsonb data-corruption bug shipped with a green suite: the one Postgres test in the tree returned early unless `TEST_POSTGRES_URL` was set, and nothing set it. Like the Redis and NATS helpers, this one is unconditional — Docker is a hard requirement of the test run rather than something a flag opts into. (WI-183)
- `inEntrySpan(name, fn, tracer, options)` in `@onebun/core` — re-roots the trace like `inRootTraceScope` and opens a span for the work, for your own background boundaries. And three tracing switches alongside `traceHttpRequests`, all `true` by default: `tracing.traceQueueMessages`, `tracing.traceScheduledJobs`, `tracing.traceWebSocketEvents`. (WI-273)
- `bun run docs:typecheck` compiles every TypeScript fence in `docs/` against the real packages, and runs in CI. Nothing had ever type-checked the documentation — `tsc` only admits `.ts` and the VitePress build only highlights syntax — so a page could import a removed export or name an option that does not exist indefinitely. The first run found 120 such errors across 20 pages. Deliberate fragments are marked with `<!-- typecheck: skip -->` above the fence; a baseline records today's backlog so the gate fails on new drift. (WI-311)
- The `onebun-framework` agent skill is now part of the repository at `skills/onebun-framework`, installable with `bun run skill:install` and checkable with `bun run skill:check`. It previously lived only in `~/.claude/skills`, which is gitignored — it appeared in no diff, no CI step could see it, and it drifted a full day behind the documentation. `bun run docs:typecheck` now compiles its snippets alongside `docs/`, so a wrong recipe in the file an assistant reads before writing OneBun code fails the build. See the Agent Skill section of `docs/ai-docs.md` for installation, including how to point it somewhere other than `~/.claude/skills`. (WI-316)
- **`tryDeleteDurableConsumer()` — the teardown form of `deleteDurableConsumer()`, which never throws.** The strict form is right for a call you make on purpose and wrong for one an `afterEach` makes unconditionally. It opens with a connection check and resolves the stream strictly, so on an adapter that never connected, after a case failed before `connect()`, or on a pattern no declared stream binds, it throws — and **a throw inside `finally` replaces the exception already in flight**. The assertion that actually failed disappears from the output behind a JetStream error from the cleanup. ```typescript afterEach(async () => { await adapter.tryDeleteDurableConsumer('orders.created', 'order-processors'); }); ``` Not connected is a quiet `false` — nothing was attempted, so reporting it would make every clean teardown noisy. Anything else that goes wrong, including a permissions denial or a mistyped pattern, is a `false` plus an `onError` event: swallowed for the caller, not for a listener. A hand-rolled `try { … } catch {}` around the strict form achieves the first half and loses the second. It calls the strict form and adds nothing but the guard and the catch, so the two cannot drift. `deleteDurableConsumer()` is unchanged and is still the one that refuses to be quiet. **`getLayer()` takes `[ServiceClass, token]` pairs.** An Effect `Context` has exactly one slot per service class, so an application holding two instances of one class — two named registrations, or two service classes that happen to share a name — does not fit in one. `getLayer()` refused rather than handing back whichever instance was merged last, which left Effect-level composition with no way forward at all: `getService(Class, token)` could name an instance, `getLayer()` could not. ```typescript const layer = app.getLayer([[MailerService, PRIMARY_MAILER]]); await Effect.runPromise(Effect.provide(program, layer)); ``` The layer still holds one instance per class — that is what a `Context` is — but which one is now yours to state rather than a function of module import order. Every ambiguous class must be named; leaving one out still refuses, and the message lists only what is still unresolved rather than sending you back to fix something you had already fixed. Naming an unambiguous class is allowed and simply pins what was going to be there anyway. This makes a multi-database or multi-cache application composable from outside the module tree — an Effect-native integration test, a script, an embedding host — for the first time. (WI-324)
- 295 behavioural tests now pin the documented recipes, taking snippet coverage from 233/497 to 491/497. They live in 21 new per-area `docs-examples.test.ts` / `docs-coverage.test.ts` files — one per core subdirectory and per package — rather than in the 6000-line root file. Each carries `@source docs:<page>#<section>` and asserts what its section promises: the response body, the metadata actually registered, the error actually thrown, the handler that did or did not run. An adversarial pass then mutated the framework sources in throwaway copies and proved 44 of the new assertions could not fail; 27 were repaired, 3 removed, and the rest were confirmed load-bearing. The coverage baseline is tightened from 264 uncovered snippets to 6. (WI-330)
- A `.githooks/pre-commit` hook regenerates README.md and stages it when a commit touches something it is generated from — a marked region in `docs/`, a package manifest, the template or the generator. Without it, editing a docs region cost a round trip through CI: push, `readme:check` goes red, regenerate, commit again. - **CORS preflight is now answered before routing, so `cors` works without an `@Options()` route on every path.** With `cors` configured, a browser preflight to a path whose controller declared only `@Get()` or `@Post()` came back a bare **404 with no `Access-Control-*` headers**. The browser then blocked every cross-origin request carrying `Authorization` or a JSON content type — which is most of them. A path that did not exist behaved the same way, so a frontend got an opaque failure instead of a well-formed answer. The cause was placement rather than logic: `CorsMiddleware` is correct, but global middleware is concatenated into **registered route handlers only**, and an unrouted `OPTIONS` never reached one. Preflights are now answered at the top of the server's fallback, before anything else looks at the request: - **No `@Options()` route is needed** on the paths your frontend calls. - **A declared `@Options()` route is never shadowed.** Bun's router runs first, so a matched path never reaches the fallback. - **Socket.IO paths are covered.** The short-circuit sits ahead of the WebSocket block, because the Socket.IO path check is method-agnostic — a cross-origin `OPTIONS /socket.io/...` used to enter the upgrade path, fail, and answer 400 with no CORS headers. - **Rate limiting never sees a preflight.** It already never did on the routed path, since CORS sits first in the chain and answers without calling `next()`. The two paths are now consistent. - **`preflightContinue: true` opts out entirely** — the short-circuit does not fire and the previous behaviour is preserved, because that option exists so a downstream handler produces the response. **Also changed: `CorsMiddleware` no longer swallows every `OPTIONS`.** It answered 204 to any `OPTIONS` without calling `next()`, so a declared `@Options()` route was unreachable whenever `cors` was configured, and a plain API-discovery probe got a CORS response instead of your application's. Both the middleware and the short-circuit now gate on `Access-Control-Request-Method`, which the Fetch spec requires on every real preflight. A `curl -X OPTIONS` reaches your handler, or an honest 404 where you declared none. A real preflight is still answered by CORS even where an `@Options()` route exists — a preflight response that does not carry the grant is a blocked request whatever its status. Use `preflightContinue: true` to handle preflights yourself. (WI-185)
- **Routes on `@Controller('/')` no longer 404.** `@Controller('/')` combined with `@Get('/health')` registered `//health`, which matches **nothing** — not `/health`, and not `//health` either. A whole controller silently disappeared, and the startup log printed `Mapped {GET} route: //health`, confirming the broken path to whoever wrote it. Path composition was a plain string concatenation of prefix + controller path + route path. `normalizePath` strips a *trailing* slash, so a duplicate in the middle survived. `joinRoutePath` now collapses runs of separators wherever the three meet, so no combination of them can produce a path that matches nothing. `@Controller('/')` and `@Controller()` are equivalent. **This is also the real cause of the reported "a root wildcard does not match nested paths" behaviour.** Raw `Bun.serve({ routes: { '/*': { OPTIONS } } })` matches nested paths perfectly well — verified directly. The failure was `@Controller('/') + @Options('/*')` composing to `//*`. The documented workaround of using a prefixed wildcard happened to sidestep the composition rather than a router limitation. **The OpenAPI generator uses the same helper now**, and that fixed a second divergence nobody had reported: it composed paths *without* normalizing, so `@Controller('/users') + @Get('/')` was documented as `/users/` while the server had always served `/users`. Nine assertions across the docs tests were pinning that mismatch. A route is now documented at the path it actually serves. If you generate clients or write integration tests from the OpenAPI spec, paths that previously ended in a trailing slash no longer do — they now match the server, which never had one. (WI-186)
- **`sql.placeholder()` on a `json`/`jsonb` column stored the internals of a drizzle `SQL` object** — the prepared-statement path corrupted differently and worse than the value path: `fillPlaceholders` pushes whatever the column encoder returns straight into the parameter array, with none of the unwrapping the value path does, so the serialized query chunks of an `SQL` instance were written to the column. A json/jsonb placeholder now round-trips through `.prepare()` on both `.values()` and `.set()`, one prepared statement can be executed any number of times with different payloads, and an explicit `null` binds SQL NULL rather than the JSON text `null`. - **⚠️ `json`/`jsonb` columns were stored double-encoded on PostgreSQL, and the on-disk format changes** — every value written to a pg `json`/`jsonb` column through `DrizzleService` landed as a jsonb **string**: `jsonb_typeof` answered `'string'`, `@>` matched nothing, and `jsonb_array_length` failed with `cannot get array length of a scalar`. ### Security

- **BREAKING SECURITY: `auth: { type: 'onebun' }` is rewritten. The previous scheme authenticated nothing.** It signed `[method, url, timestamp, nonce, serviceId]` and verified a payload rebuilt from `x-onebun-method` and `x-onebun-url` — headers no client ever sent. The verifier therefore always reconstructed `GET` + `/`, so **only a literal `GET /` could validate**. Every POST, every path, every request worth protecting failed to verify. The suite passed because three tests hand-injected the two phantom headers before verifying, so they exercised a protocol the client did not speak. Three further defects went with it, and each of them changes what is on the wire, so all four are fixed together: - The query string was not covered — it was appended after signing, so `?role=admin` could be added to a captured request without invalidating anything. - The body was not covered at all. - The nonce was generated and transmitted but never recorded, so a captured header set replayed for the full five-minute window. The age check also accepted arbitrarily *future* timestamps. - Signatures were compared with `===`, which short-circuits on the first differing character. **The new format** is one self-describing header: ``` X-OneBun-Signature: v=1;svc=orders-service;kid=default;alg=hmac-sha256;aud=billing-service;ts=…;nonce=…;sig=… ``` The signature covers the method, path, query string exactly as sent, `Content-Type`, every byte of the body, and the whole parameter line. Fields are length-prefixed with a fixed arity, so no value can be smuggled across a field boundary however many delimiters it contains. The MAC key is derived as `HMAC(secret, "OneBun-Auth-v1")`, so the same secret used for anything else cannot produce a value that verifies here. Comparison is constant-time. **New: `audience`.** Bind each signature to its callee. Without it, a request captured en route to one service replays perfectly at another that shares the secret — which is the default shape when a fleet is handed one `secretKey`. **New: `keyId`.** Rotate a secret without a flag day; a verifier can accept the old and the new key at once. **Migration.** `validateOneBunAuth` is **removed**, not deprecated — it took only headers, so the method, path, query and body it needs were not in its arguments and it could not be made to work. Use `verifyOneBunRequest`, which takes the request. `audience` and `nonceStore` are required options, and `false` is a legal value for each: both defend against attacks a default would silently leave open, so going without is written down in your code rather than inherited. An old caller against a new callee fails with `reason: 'legacy-unversioned-signature'` rather than mysteriously. **Also fixed, same root cause:** `auth: { type: 'apikey', location: 'query' }` never reached the wire. The URL was built one line before auth ran and never rebuilt, so the key was added to a config the request no longer used. Every such call went out unauthenticated, with no error — only 401s from an API the caller believed it had authenticated to. (BREAKING, WI-292)
  - Migration: Both ends must move together — the wire format changed and neither direction interoperates. A caller still on the previous release fails against a new callee with `reason: 'legacy-unversioned-signature'` and a 401. A caller on the new release sends only `X-OneBun-Signature` and no longer sends `X-OneBun-Service-Id`, `X-OneBun-Timestamp`, `X-OneBun-Nonce` or `X-OneBun-Algorithm`, so any verifier still reading those four sees them missing and rejects. There is no version in which both are accepted. Roll out callee-first and have the callee log `result.reason` without answering 401 until every caller is upgraded; the library has no observe mode, so that window is yours to open and to close. **On the callee.** `validateOneBunAuth` is removed, so the build breaks — that is the signal. Replace it with `verifyOneBunRequest({ method, url, headers, body }, { secret, audience, nonceStore })` from `@onebun/requests`. It takes the request, not a header set, because the method, path, query and body it must check are not in a header set. Read the body yourself, with a size cap — you are hashing unauthenticated input — and pass the same bytes that arrived. `audience` and `nonceStore` have no defaults; pass `false` explicitly if you are going without. `makeSingleReplicaNonceStore()` is correct for a single replica only: behind N replicas a captured request is accepted once per replica per freshness window, so supply your own `OneBunNonceStore` backed by shared storage. Map the outcome with `oneBunAuthFailureStatus(reason)` — 401, or 503 when your own store is full or unreachable — and keep `result.reason` in your logs, never in the response body. **On the caller.** Add `audience: '<the callee's service id>'` to every `auth: { type: 'onebun' }` block whose callee does not run `audience: false`. Omit it and the signature carries an empty `aud=` and is refused with `audience-mismatch` — a 401, not a warning. Check that `serviceId`, `keyId` and `audience` match `[A-Za-z0-9_.:-]{1,64}`: the signer does not validate them, so a `serviceId` like `orders service` still produces a header and the callee rejects it as unparsable. Rename such ids before you upgrade. **Clocks now matter.** The freshness window is 60s rather than 300s, and a timestamp more than 5s ahead is refused outright where the old check accepted any future value. Run NTP on both ends, or widen `maxAgeMs` / `maxSkewMs` on the verifier. Do nothing and every `onebun`-authenticated call across the version boundary returns 401 from the moment one side is upgraded. Separately, `apikey` with `location: 'query'` needs no code change, but those calls were going out with no key at all and now carry one: requests that have been failing start succeeding, and the key starts appearing in the callee's access logs and in every proxy in between. Move it to `location: 'header'` if that is not acceptable.
- **SECURITY: the default exception filter no longer puts a stack trace in the 500 response body.** Any throw that was neither an `HttpException` nor a `OneBunBaseError` produced a response whose `details` carried the error's full `stack`, its class name and its non-HTTP `code`. Set it explicitly or it stays off, including in production images that happen to set `NODE_ENV=development`. `HttpException` and `OneBunBaseError` responses need no attention: their `details` was `{}` before this change and stays `{}` with the flag on. Multi-service applications cannot opt in through options: the orchestrator constructs each child application without `exposeErrorDetails`, and `MultiServiceApplicationOptions` does not accept the field, so passing it fails typecheck. If you need the details in one of those, attach a filter yourself — `@UseFilters(createDefaultExceptionFilter({ exposeErrorDetails: true }))` on the controller.
- **⚠️ The default 500 body no longer echoes the error's message, which was disclosing paths, hosts and credentials** — for any unhandled throw the response carried `error.message` verbatim, and that text is written by whatever threw it rather than by the author. Reproduced end to end against a running application: `ENOENT: no such file or directory, open '/srv/app/config/private.pem'` (an absolute path), `connect ECONNREFUSED 10.0.3.17:5432` (an internal host and port), `getaddrinfo ENOTFOUND internal-billing.svc.cluster.local` (the service topology) and `Invalid URL: postgres://app:hunter2@db.internal:5432/app` (a password) all reached an unauthenticated caller who could provoke a 500. Driver errors quote the failing statement and sometimes its bound parameters. The unhandled branch now answers with the fixed string `'Internal Server Error'`, exported as `UNHANDLED_ERROR_MESSAGE`. `HttpException` and `OneBunBaseError` are unchanged — those messages are author-written and client-facing, and the leak was confined to the branch where the text came from a library or the kernel. Filtering by pattern was considered and rejected: a denylist always misses the shape it has not met, and reads as safe. (`@onebun/core`) (BREAKING, WI-345)
  - Migration: A client that reads `error` from a 500 body to distinguish failures now sees one constant string. Two supported ways forward: - **Say it deliberately.** `throw new HttpException(422, 'orderId must be a positive integer')` answers with that text verbatim. Catching a driver error and rethrowing it as an `HttpException` you worded yourself is the intended pattern for a specific client-facing message. - **Turn disclosure back on where it is safe.** `exposeErrorDetails: true` in `ApplicationOptions` returns the real message alongside the stack. It is one flag for both — a message naming an internal host is not meaningfully safer than the stack naming the file — and it is deliberately not derived from `NODE_ENV`, so an unset or mistyped variable cannot enable it by accident. Nothing changes for operators: the application already logged the whole error, message and stack included, before the filter ran, and a test now pins that.
- **SECURITY: a URL fragment could inject and override `@Query()` parameters.** OneBun parsed the request target with two parsers that disagreed about the fragment. The router uses `new URL(req.url)`, which correctly drops everything from `#`. The `@Query()` extractor searched the raw string for `?` and had no concept of a fragment at all, so it fed everything after the first `?` — fragment included — to `URLSearchParams`. Anyone able to write a request target could therefore hand a handler parameters the router never saw: ``` GET /api/search#?admin=true -> router: no query @Query('admin'): 'true' ``` And because `URLSearchParams` is last-wins, a **real parameter could be overridden**, not merely added: ``` GET /api/search?page=1#&page=99 -> router: page=1 @Query('page'): '99' ``` Confirmed end to end: Bun passes the fragment through into `req.url` verbatim. A browser strips it before sending; nothing else has to, and an in-path attacker writes the request target directly. No secret and no authentication scheme were involved — every application using `@Query()` was affected, and validation did not help, since the injected values went through the same pipeline as legitimate ones and were validated as real input. Any authorization or logging decision made from `new URL(req.url)` disagreed with what the handler actually acted on. The fragment is now cut before the query is located, so `@Query()` and the router see the same thing. A percent-encoded `%23` is still an ordinary character in a value, and a bare trailing `#` no longer ends up appended to the last parameter's value. Found while adversarially reviewing a proposed HMAC signing scheme, whose claim that "the bytes signed are the bytes on the wire" turned out to be false for a reason outside the scheme. (WI-349)

### Read This First

Fifteen entries below are breaking, and several describe silent data loss rather than a failure you
would have noticed. Each carries its own **Migration** note where it appears; this is the index.

- **SQLite `transaction()` never rolled back** — an async callback committed at its first `await`, so
  a throw left every row it had written. Multi-statement operations were not atomic.
- **SQLite `.get()` on a join transposed columns** when two tables shared a column name — an order's
  total came back holding a user id, with HTTP 200.
- **`@onebun/requests` retried POST and PATCH by default** — an unconfigured charge was sent up to
  four times.
- **Validation failed open with two `arktype` copies** — a rejected body was answered 200 with the
  error objects as the payload.
- **`@UseGuards` was ignored on WebSocket and queue handlers** — consumers ran unguarded while the
  migration guide promised parity.
- **Rate limiting trusted `X-Forwarded-For` unconditionally** and bucketed every direct caller
  together; the limit came off by rotating a header.
- **A configured backend is now required at startup** — an unreachable Redis or database fails
  `app.start()` instead of degrading silently. Opt out with `allowDegradedStart`.
- **Shutdown drains in-flight requests** before destroy hooks; `@Global()` services, module
  construction, `TestingModule.overrideProvider()` and JetStream acknowledgement policy all changed
  shape. See the entries for the migration steps.


### Added

- **The JetStream dead-letter queue is implemented** (`@onebun/nats`) — `supports('dead-letter-queue')` returned `true` while `SubscribeOptions.deadLetter` was read nowhere in the adapter: `queue` was ignored outright and `maxRetries` was ignored twice over, so a repeatedly failing message was left for the server to exhaust and the configured dead-letter stream stayed permanently empty. `deadLetter.maxRetries` now participates in the consumer's `max_deliver`, resolved as `retry.attempts` → `deadLetter.maxRetries` → `consumerConfig.maxDeliver` → `3`. `retry.attempts` stays ahead of it so every configuration written before this release keeps the exact `max_deliver` it had. On the delivery the server would otherwise have made the last, the payload is republished to `deadLetter.queue` and the original is terminated. The same routing applies to `message.nack(false)` — and the bare `message.nack()`, which means the same thing — under `ackMode: 'manual'`, matching what the Redis adapter already does for `onNack(false)`; `nack(true)` still asks for redelivery. The copy is published BEFORE the original is terminated: if the republish fails the original is left exactly as it was for the server to redeliver or exhaust, and the failure is reported to `@OnQueueError`, because losing the payload is the one outcome a dead-letter queue exists to prevent. The republished message keeps its original `id` and gains `dlq.originalPattern`, `dlq.deliveryCount` and `dlq.error` in `metadata`. Note that `term()` removes the original only under `retention: 'workqueue'` and `'interest'`; under the default `retention: 'limits'` the payload stays in the source stream until retention evicts it, and the dead-letter copy is durable either way. The Redis adapter still ignores `deadLetter.queue` and `deadLetter.maxRetries`, routing to `queue:dlq:${pattern}`; aligning it is tracked separately. (BREAKING, WI-199)
  - Migration: `deadLetter.queue` must be a literal subject bound by a declared stream. A wildcard (`*`, `#`, `>`), or a queue equal to the subscription's own pattern, now throws from `subscribe()` at startup instead of failing on the first dead letter. A consumer configured only through `deadLetter.maxRetries` is reconciled to a new `max_deliver` on the next startup.
- **`deleteDurableConsumer()` on the JetStream adapter, and the consumer lifecycle is finally documented** (`@onebun/nats`) — `unsubscribe()` and `disconnect()` deliberately never remove a durable consumer, because they run on every graceful shutdown and deleting there would discard the consumer's position on each deploy. That left no supported way to decommission one at all. There is now: ```ts const adapter = queueService.getAdapter() as JetStreamQueueAdapter; await adapter.deleteDurableConsumer('orders.created', 'order-processors'); ``` It returns `true` when a consumer was removed and `false` when there was none, so it is safe to call twice, and it rethrows a permissions denial rather than reporting it as "already gone". Stream resolution is strict here: if no declared stream binds the pattern it throws and names every stream the application declares, instead of falling back to the first one the way `publish()` and `subscribe()` do — on a destructive call a mistyped pattern must not delete a consumer on an unrelated stream. The downcast is needed because only JetStream has durables, so the method is not on the `QueueAdapter` interface. The documentation now states the contract that was missing. **A `group` names a permanent server resource on JetStream** — the durable is named from the group and the pattern together, so a group templated per run or per deploy (a build number, a pod name, a timestamp) leaves a new orphaned consumer behind every time, each holding its own position and `max_ack_pending` budget. Name the role, not the deployment. The same option means something different on `NatsQueueAdapter`, where it is a stateless NATS queue group that dies with its members — one transient, one permanent, previously unstated anywhere. Re-subscribing after a delete creates a fresh durable with `deliver_policy: new`, so the old position is gone for good. (WI-200)
- **`PublishOptions.messageId` now enables JetStream deduplication, plus `StreamDefinition.duplicateWindow`** (`@onebun/nats`) — `messageId` was an inert echo. It reached the message body and came back as `Message.id`, but JetStream keys deduplication strictly off the `Nats-Msg-Id` header, which was never sent: `js.publish` was called with two arguments and no publish options at all. Publishing the same logical message twice stored it twice, so an outbox could not be replayed safely. A caller-supplied `messageId` is now sent as `Nats-Msg-Id`, and the server drops a second message carrying an id it has already seen inside the stream's deduplication window. Only a supplied id enables it: when `messageId` is omitted — or empty — the adapter generates one, uses it as `Message.id` and sends no header, because a generated id is unique per call and would only grow the server's deduplication index. The id also stays in the JSON body, so the wire format is unchanged and existing consumers are unaffected. On the memory, Redis and core-NATS adapters `messageId` is still echoed back as `Message.id` and nothing more. `StreamDefinition.duplicateWindow` (nanoseconds, matching `maxAge`) sets that window per stream; `streamDefaults.duplicateWindow` applies it to every stream that does not declare its own. Omitted, the server's own default of two minutes applies — usually too short for an outbox that has to survive a crash and a restart. It is sent only when declared, on both the create and the update path, so a window an operator configured out of band is never reset by a deploy. (BREAKING, WI-206)
  - Migration: A `messageId` reused within the stream's deduplication window is now silently rejected by the server: the second message is NOT stored, while `publish()` still resolves normally with no error and no local signal. Code that reused a non-unique `messageId` — a constant, a per-batch id, a value derived from something coarser than the message itself — previously stored every copy and now stores only the first. Audit any caller that passes `messageId` and make sure it is genuinely unique per logical message, or drop the option. The window defaults to two minutes and can be widened per stream with `duplicateWindow` (nanoseconds).
- **`ackTimeout` on `@Subscribe` — an acknowledgement deadline per subscription** — `SubscribeOptions.ackTimeout` sets how long the server waits for an acknowledgement before it redelivers, for one subscription. The only knob before was `consumerConfig.ackWait`, which applies to every consumer the application creates, so a handler that takes minutes and one that takes milliseconds had to share a window sized for whichever mattered more. Each side of the boundary keeps its own unit — ackTimeout is in milliseconds; consumerConfig.ackWait is in nanoseconds — and the adapter multiplies by 1_000_000 on the way to the wire. JetStream resolves the consumer's `ack_wait` as `ackTimeout -> consumerConfig.ackWait -> DEFAULT_ACK_WAIT_NANOSECONDS` (30 seconds), so an application that sets neither is unaffected. Because `ack_wait` is one of the fields the reconciliation stamp hashes, a changed value is applied to an existing durable consumer automatically on the next start — no `nats consumer rm` in between — and the consumer's name is unchanged, since a timeout is configuration and not identity. Two processes that disagree on it still fail startup with a reconcile-cycle error, which now reports each diverging field with both values (`ack_wait (this process 45000000000, on server 30000000000)`) rather than only the two config hashes, which name the writers but say nothing an operator can act on. The option is inert under ackMode: 'none', where the server tracks no acknowledgements and there is nothing to time out, and the in-memory, Redis and core-NATS adapters ignore it, having no server-side acknowledgement window at all. Keep it above the slowest run of the handler: a window that expires while the handler is still working redelivers the message and does the work twice. The shutdown drain remains a fixed 30 seconds, so a handler granted a longer `ackTimeout` can still be abandoned by a deploy (`@onebun/core`, `@onebun/nats`) (WI-207)
- **`ackMode: 'none'` — fire-and-forget delivery** (`@onebun/core`, `@onebun/nats`) — `SubscribeOptions.ackMode` accepts a third value. Under `'none'` a message is delivered exactly once and nothing is acknowledged, so there is no redelivery and no dead-letter routing on any adapter. Choose it when losing a message costs less than processing it twice — a telemetry firehose, where a replayed sample is worse than a missing one. Everything that depends on the broker tracking delivery state goes inert with it: `retry` (including `retry.attempts`), `deadLetter`, `ack_wait`, `max_deliver`, and the `attempt`, `maxAttempts` and `redelivered` fields on `Message`. A handler that throws still emits `onMessageFailed`, so failures stay observable; the message is simply not retried. `message.ack()` and `message.nack()` become no-ops. Per adapter: JetStream creates the consumer with `ack_policy: none` and omits `ack_wait`, `max_deliver` and `max_ack_pending` from the wire entirely — the server accepts them but ignores them, and sending them would record a redelivery policy that cannot occur. Redis skips both the requeue and the dead-letter branch. The in-memory adapter suppresses `nack(true)`, which would otherwise resurrect a message in the one mode that promises a single delivery. `NatsQueueAdapter` gains nothing on the wire, because core NATS never had an acknowledgement protocol — `'none'` is simply the only mode that describes it truthfully, while `'auto'` and `'manual'` remain accepted there with no transport effect. `'auto'` and `'manual'` are unchanged: both still map to `AckPolicy.Explicit` on JetStream and decide only *who* acknowledges. Nothing needs to change in existing code. (WI-212)
- **`migrationsTable` and `migrationsSchema` — one journal per migration set** — a package that ships migrations for its own tables could not have its own journal, so every migration set in a process landed in drizzle's single `drizzle.__drizzle_migrations`. That is not merely untidy: drizzle decides whether to apply a migration by comparing the timestamp baked into its folder against the **newest row** in the journal, never by hash. Two folders sharing one journal therefore skip whichever set was generated earlier — no error, nothing logged, and the application starts and then fails at the first query against a table that was never created. Both options are now accepted by `runMigrations()`, by `DrizzleModule.forRoot()` and through `DB_MIGRATIONS_TABLE` / `DB_MIGRATIONS_SCHEMA`, and are forwarded on every path that runs migrations including the automatic ones. `migrationsSchema` is PostgreSQL-only and ignored on SQLite, which has no schemas. Because the option exists to prevent a silent loss, it ships with the guard that makes the mistake impossible to hit quietly: a second, different `migrationsFolder` that would claim a journal another folder already owns is refused, naming both folders and the option that separates them. Several journals in one process is the supported shape — that is the point — while several folders sharing one journal is not, and re-running the same folder stays idempotent. Migrations whose journal entries end up neither applied nor already recorded now emit a `warn` naming each file, so a skipped set is visible even where the sharing is deliberate. Two repairs ride along. `getAppliedMigrationHashes()` was dead on PostgreSQL: it read `.length` off Bun's lazy SQL thenable without awaiting it, so the result was always an empty set, and it queried an unqualified table name where drizzle puts the journal in its own schema. PostgreSQL therefore reported `0 migrations applied` no matter what actually ran — precisely the signal an operator would use to notice the skip above. It is now awaited, schema-qualified and reads the configured table, and a genuine query failure is logged at `debug` instead of vanishing into a bare `catch`. And `migrationsTable`/`migrationsSchema` are validated as plain SQL identifiers before use, since a table name cannot be a bound parameter and reaches the query as text (`@onebun/drizzle`) (WI-223)
- **`connectionString` for PostgreSQL, and `DB_URL` stops losing its query parameters** — the documentation described a `connectionString` option for `DrizzleModule.forRoot()` that `PostgreSQLConnectionOptions` did not have and `initialize()` ignored, so a reader who followed it got a connection assembled from undefined discrete fields and no error naming the cause — the failure arrived as an unreachable server. The option now exists, as a discriminated shape: `connectionString` **or** the five discrete fields (`host`, `port`, `user`, `password`, `database`), never a mix and never a subset. The excluded keys are typed `never` on each branch, so a half-filled object is a compile error at the call site rather than a connection failure later, and the question of which wins when both are supplied cannot arise. Options reaching `initialize()` from an untyped source — a JSON config, a cast — are validated there and rejected with a message naming which discrete fields accompanied a URL, or which of the five are missing; neither is resolved by picking a winner silently. Separately, and worth checking on any deployment that sets it: `DB_URL` was parsed into those five fields and the URL then reassembled from them, which discarded everything after the path. A `DB_URL` of `postgresql://user:pw@host:5432/db?sslmode=require` reached the driver as `postgresql://user:pw@host:5432/db` — **connecting without SSL, silently**. The URL is now passed through untouched, so `sslmode`, `application_name` and any other query parameter apply. `DB_TYPE` and `DB_URL` are also documented for the first time; both were implemented and missing from the Environment Variables table (`@onebun/drizzle`) (WI-227)
- Named module registrations: `DrizzleModule.forRoot({ ..., as: TOKEN })` configures one database under a token and `DrizzleModule.forFeature(TOKEN)` selects it in a feature module. Each registration gets its own options and its own `DrizzleService` instance, so two databases in one application finally work — with plain constructor injection and no token at the injection site, because the module's import already decided which registration its providers resolve to. Registering one token twice throws instead of silently replacing the first; selecting a token no `forRoot()` configured fails at startup naming the missing call; a module that selects two registrations of one service refuses to start naming both. A named registration is never global — that is what makes two of them safe. Applications with a single unnamed `forRoot()` are unchanged. (WI-237)
- `@Inject(TOKEN)` picks which named registration a constructor parameter gets, for the one module that legitimately needs two of them (a reconciliation job, a migration). Un-annotated parameters in the same constructor still resolve by type — the token lives in a side map, so `design:paramtypes` is untouched and partial injection is unaffected — and controllers work too, since `@Controller`'s wrapper subclass carries the map. Asking for the bare class in such a module throws at startup naming both candidates; asking for a token the module never selected throws naming what it did select. `CacheModule` gets the same `forRoot({ as: TOKEN })` / `forFeature(TOKEN)` as `DrizzleModule`, so two caches with different sizes or backends no longer collapse onto the last configuration. `app.getService(Class, TOKEN)` reaches a registration from outside the module tree; `app.getLayer()` remains single-valued per class name and has no token form. Combining `as` with `isGlobal: true` throws — a named registration is never global. (WI-237)

### Changed

- `exports: [SomeModule]` now throws `OneBunInvalidExportError` naming both modules. The NestJS module re-export idiom was silently discarded — `getServiceTag()` throws for a module class and the throw was swallowed — so a re-exported module contributed nothing to its importer. (BREAKING, FB-6)
  - Migration: The entry was always a no-op, so nothing that relied on it was working: an importer either failed at a controller with no mention of the export, or also imported the module directly and silently got a second copy of every provider. Remove the module from `exports` and import the providing module directly wherever its services are needed.
- Queue enabling now has three paths instead of two. An application that configures `queue.adapter`, `queue.options` or `queue.redis` without setting `queue.enabled` now constructs and connects that adapter during `app.start()`. Previously the queue was enabled only when a controller carried a queue decorator (`@Subscribe`/`@Cron`/`@Interval`/`@Timeout`) or when `queue.enabled: true` was set explicitly, so a producer-only application booted with the queue silently disabled and every `publish()` was discarded. Operator consequence: such an application will now fail to boot if the broker is unreachable, where it previously started successfully and dropped messages. `queue.enabled: false` combined with an explicit adapter configuration keeps the queue disabled and logs a single warning naming the contradiction. It is not an error and does not stop startup — the explicit `enabled: false` always wins. The multi-service orchestrator resolves the enable decision once, before starting any service, and passes the resolved value to every child application, so a child can no longer reach a different answer than its siblings by re-deriving the decision from its own module graph. `QUEUE_NOT_ENABLED_ERROR_MESSAGE` was rewritten to name all three enabling paths and the `enabled: false` override. Code that matches on that literal text must be updated; code that compares against the exported constant is unaffected. (BREAKING, WI-184)
  - Migration: If you configure a queue adapter but do not want the queue running, set `queue.enabled: false` explicitly — the adapter is then never constructed and a warning names the contradiction. If your application configured `queue.adapter`/`queue.options`/`queue.redis` and relied (knowingly or not) on the queue staying off, it will now connect to the broker at startup and fail to boot when the broker is unreachable. Anything asserting on the literal text of `QUEUE_NOT_ENABLED_ERROR_MESSAGE` must switch to comparing against the exported constant.
- `@Global()` module services are now scoped per application — and per sub-application in multi-service mode — instead of per process. Two applications in the same process each construct their own instance, so a second `DrizzleModule.forRoot()` or `CacheModule.forRoot()` opens its own connection rather than silently reusing the first application's. The options a dynamic module is imported with are likewise captured per application at import time. (BREAKING, WI-187)
  - Migration: Code that relied on one application's `@Global()` service instance leaking into a later application in the same process will now see a fresh instance. This mostly affects test suites that booted several applications and expected shared state; assert on each application's own `getService()` result instead.
- `TestingModule.overrideProvider()` now replaces the provider in every module. It previously reached root-module controllers only: a service that injected the overridden class, or anything inside an imported module, was **silently ignored** and kept the real instance — the mock was accepted and then bypassed without a warning. The real provider is no longer constructed at all when an override replaces it, and lifecycle hooks on a `.useClass()` mock fire exactly once. (BREAKING, WI-187)
  - Migration: Tests that hand-wired around the old behaviour — constructing a service manually because the override did not reach it — can now use the override directly. A test that passed because the mock was ignored will start seeing the mock.
- SUPERSEDES the durable naming described in the pending entry for the consumer-identity change: that entry says a durable is named `${group}--${filterSubject}`, which is no longer the shipped form. Whoever compiles the release notes should describe only the scheme below — both changes ship in the same unreleased version, so users migrate once. A durable JetStream consumer is named `${group}--${filterSubject}--${digest}`: the group and the filter subject with every character outside `[-\w]` replaced by an underscore, followed by a 12-character digest of the raw pair. The digest is load-bearing, not decoration. Sanitising the readable part is lossy — `orders.*` and `orders.>` both reduce to `orders__`, as do `orders.new` and `orders_new`, and `--` is itself a legal character sequence inside a group name. Without the digest, two subscriptions whose patterns differ only in those characters resolved to one consumer: the second reconciled it onto its own filter subject and the first stopped receiving anything, with no error on either side. That is the same silent takeover the per-(group, pattern) naming was introduced to end, surviving for the most ordinary wildcard patterns. Behaviour that does not change: the same group with the same pattern still resolves to one durable, so several instances of a service still share the work. Patterns that differ only by `#` versus `>` also still share a durable, because `#` is rewritten to `>` before the name is built — they are the same NATS subject. (BREAKING, WI-218)
  - Migration: No additional migration beyond the one the consumer-identity change already requires: delete the durable consumers created by earlier releases with `nats consumer rm <stream> <consumer>` and let the application recreate them. Because both changes ship in the same unreleased version, there is no intermediate naming scheme any deployment will have seen — do the deletion once.
- **`bun test` no longer collects coverage; use `bun run test:coverage`** — coverage instrumentation in Bun intermittently spins the test process forever while loading a large module graph: no output at all, every timer in the process dead (so `--timeout` and testcontainers' own startup timeouts never fire), and SIGTERM is not serviced, so the run has to be SIGKILLed and leaves a core burning until it is. Measured at roughly 4 hangs in 9 runs. The everyday `bun test` no longer pays that cost and is now reliable — 5/5 consecutive clean runs of `bun test packages/nats` and 3/3 of the full suite, where the full suite previously hung on most attempts. Coverage moved to its own command, `bun run test:coverage`, and the CI step that feeds the Codecov badge retries a hung run up to four times while still failing immediately on a genuine test failure. Note for anyone touching `bunfig.toml`: the `coverage` key is deliberately absent rather than set to `false`, because `false` silently overrides `--coverage` and produces no lcov at all. Separately, `mock.module` is now banned in this repo's tests — the replacement is process-global and wedged every other file in the same run, including the integration suites that need the real client. (WI-219)
- **`testcontainers` is a required peer dependency of `@onebun/core`, not an optional one** — it was declared `peerDependenciesMeta.optional: true` while the `@onebun/core/testing` barrel value-imports it at module scope, so a consumer who believed the manifest and skipped it got a module-resolution failure from the first import of `createTestService` or `TestingModule` — helpers that have nothing to do with containers. The declaration now matches the code. This is deliberate rather than a concession to the coupling: OneBun treats integration tests against real dependencies as the default way to test a service, and ships the container helpers to make that the path of least resistance, so the `./testing` subpath is a boundary of concern rather than a way to make the peer conditional. It stays a peer rather than moving into `dependencies` precisely so it does not become a runtime cost — a Docker client in `dependencies` would land in every production install of the framework, since npm has no per-subpath dependencies. Declared in your `devDependencies`, it is never resolved by a production install and never referenced from a runtime bundle. A Docker daemon is needed only to run the container helpers themselves; `createTestService`, `TestingModule`, `useFakeTimers` and the mock helpers do not require one (`@onebun/core`) (BREAKING, WI-226)
  - Migration: Add `testcontainers` to your devDependencies if you import anything from `@onebun/core/testing` and do not already have it: `bun add -d testcontainers`. Package managers will now warn about the unmet peer where they previously stayed silent. Nothing changes for production installs — the peer is not in `dependencies`, so `bun install --production` still never pulls it.
- `@Global()` modules are now constructed before a module's ordinary imports are processed. The application walks the static import graph from the root, finds every reachable `@Global()` module, and builds those first; the rest of the tree is then built as before. Two visible consequences beyond the ordering fix: a global module's providers are constructed earlier than they used to be relative to non-global ones, so `onModuleInit` on a global service now runs before that of a service in a module declared ahead of it; and a global module appears first among its parent's child modules, which affects only code reaching into `childModules` directly. (WI-232)
- A module class is now constructed exactly once per application, and `imports` decides visibility only. `forFeature()` therefore SHARES the instance instead of building a new one for each importing module — measured before: a root plus two leaves gave 3 `CacheService` instances, 3 initializations, and a value written through one was invisible through another; for `DrizzleModule` that was three connection pools. `@Global()` and non-global now differ in visibility alone: a `@Global()` module's services reach every module without an import, a non-global module's reach only modules that import it, and either way there is one instance. (BREAKING, WI-233)
  - Migration: Two consequences to check. A module's `onModuleInit`/`onModuleDestroy` now run once rather than once per importer — that is the fix for N connection pools, but a test counting hook invocations will see different numbers. And anything relying on `isGlobal: false` to obtain a fresh instance per importer now gets one shared instance; that was never a working multi-database mechanism (every instance read the same last-written configuration anyway), and a supported way to configure a module more than once is being built separately.
- `app.getService(Class)` with no token and `app.getLayer()` now throw `OneBunAmbiguousServiceError` in an application that holds two instances of one service class — two named registrations, or two service classes that share a name. Both used to answer, and which instance you got was a function of module import order. Injection is unaffected: it resolves at the module boundary, where each module has exactly one. `getService(Class, TOKEN)` is exempt. (WI-241)
  - Migration: Pass the registration token: `app.getService(DrizzleService, ANALYTICS_DB)`. Inside a service, use `@Inject(ANALYTICS_DB)`. There is no token form of `getLayer()` — an Effect Context has one slot per key, so a layer holding two instances of one class is not representable.
- A backend you configured is now required at startup. Previously `type: redis` with Redis unreachable booted the process onto a private in-memory cache — permanently, with one ERROR line — so two replicas served different data and invalidation silently did nothing; and a failed migration or an unopenable database let `app.start()` resolve, after which the server took traffic and every request returned 500. Both now fail startup, so the container dies instead of passing readiness while broken. The connection attempt is bounded by the configured connect timeout, and the error names the backend, the target with the password redacted, how long it waited, and the option that opts out. `CacheService.getBackendStatus()` reports which backend is actually serving, for a readiness endpoint to consume. A missing migrations folder is still "no migrations", not a failure. (WI-289)
  - Migration: If you rely on booting without the backend — a local run with no Redis, a container that starts before its database — set `allowDegradedStart: true` in `CacheModule.forRoot()` / `DrizzleModule.forRoot()`, or `CACHE_ALLOW_DEGRADED_START=true` / `DB_ALLOW_DEGRADED_START=true` on the environment path. The degraded start is then announced with a WARN naming the backend that is missing, rather than being silent. An application that configures no backend at all is unaffected.

### Deprecated

- `clearGlobalServicesRegistry()` and `getGlobalServicesRegistry()` are deprecated. They now operate only on the process-default scope used by a direct `new OneBunModule(...)`, never on an application's own scope, so they can no longer observe or reset what a running application holds. Assert on resolved instances — `app.getService(Class)` — instead. (WI-187)

### Fixed

- Import order no longer decides whether a `@Global()` module's services resolve, in either direction. Every global module reachable from the root's import graph is now constructed BEFORE the ordinary import loop runs, and a module that declares an already-initialized global import re-seeds from the application scope. Previously `imports: [FeatureModule, CoreModule]` — where `FeatureModule` also imports `CoreModule` — failed at boot with `Could not resolve dependency` while `imports: [CoreModule, FeatureModule]` booted; and a consumer nested inside a subtree built earlier in the same array could not see a registration that came later, at any depth. Both shapes now resolve. The pre-pass reads module metadata only and constructs no provider of its own; a global module is still built exactly once, and cyclic import graphs are handled. (FB-6)
  - Migration: Nothing to do. Applications that worked because they happened to declare the configured module first keep working; applications that failed at boot for this reason now start. If you added a static test pinning import order as a workaround, it can go.
- The queue adapter is no longer connected twice during `app.start()`. `QueueService.initialize()` called `connect()` unconditionally on an adapter the application had already connected, so every boot opened the backend connection twice. It is now guarded by `isConnected()`, matching the guard `QueueService.start()` already applied to the same call. Adapters treat `connect()` as idempotent, so this changes no behaviour beyond removing the redundant round trip to the broker. (WI-184)
- A NestJS-style object provider — `@Module({ providers: [{ provide: X, useValue: v }] })` — now throws `OneBunInvalidProviderError` naming the module and the entry. It was previously discarded by the class-provider filters, so the failure surfaced later as an unrelated `Could not resolve dependency` on whichever service expected it. (WI-187)
- Lifecycle hooks on a `@Global()` service now fire exactly once per application. `onApplicationInit`, `onModuleDestroy`, `beforeApplicationDestroy` and `onApplicationDestroy` previously fired once per module that could see the instance — five times in a five-module tree — so a `close()` in `onModuleDestroy` ran repeatedly on the same connection. (WI-187)
- `app.getService()`, `CompiledTestingModule.get()`, `getServiceByClass()`, `getServiceTag()` and `createServiceLayer()` now accept a service class whose constructor takes dependencies. The parameter type required a zero-argument constructor, so passing any service with injected dependencies was a compile error even though the lookup worked at runtime. (WI-187)
- JetStream consumers are now created with `ack_policy: explicit` for both `ackMode: 'auto'` and `ackMode: 'manual'`. They were previously created with `ack_policy: none` unless `ackMode: 'manual'` was set explicitly, and under that policy the server tracks no acknowledgements at all — so `max_ack_pending`, `ack_wait`, `max_deliver`, `message.ack()`, `message.nak()`, retry and the dead-letter queue were all inert while the documentation advertised them. A handler that threw was never redelivered. `consumerConfig.maxAckPending` was additionally never read: only `prefetch` reached the wire. Three consequences, all breaking: 1. Durable consumers created by an earlier release carry `ack_policy: none`. That field cannot be changed on an existing consumer, so `subscribe()` now detects such a durable and refuses to start rather than running with acknowledgements silently disabled. Delete the consumer and let the application recreate it: `nats consumer rm <stream> <consumer>`. 2. `subscribe()` now rejects on a genuine `consumers.add` or `consumers.info` failure. It previously wrapped the call in a bare `catch {}` that swallowed every error, including real server rejections, and carried on. A misconfigured application therefore fails to boot instead of running degraded. 3. The adapter records a configuration hash in consumer metadata (`onebun.config-hash`, `onebun.prev-config-hash`, `onebun.reconciled-at`) and reconciles a consumer only when that hash changed — an unchanged configuration now performs no update at all. Two services sharing a `group` with different `consumerConfig` or `retry` options used to overwrite each other's consumer on every start, silently and indefinitely; that is now detected as a configuration cycle and fails fast. Because consumer metadata requires nats-server 2.10 or newer, the JetStream adapter now requires that server version. (BREAKING, WI-193)
  - Migration: Before upgrading, delete every durable JetStream consumer the previous release created, or the application will refuse to start: `nats consumer rm <stream> <consumer>` for each. They carry `ack_policy: none`, which cannot be updated in place. Recreation happens automatically on the next `subscribe()`. Expect redelivery to start working. A handler that throws under `ackMode: 'auto'` is now redelivered up to `max_deliver` times (`retry.attempts` > `consumerConfig.maxDeliver` > 3) instead of being dropped after one attempt — verify that your handlers are idempotent before rolling out. If two services share a `group`, align their `consumerConfig` and `retry` options. Divergent options now raise a configuration-cycle error naming both hashes and the diverging field instead of silently overwriting each other's consumer on every start. The broker must be nats-server 2.10 or newer, which is what stores the consumer metadata the reconciliation depends on.
- `message.nack(false)` and the bare `message.nack()` now terminate a JetStream message instead of redelivering it. `nack(true)` still asks for redelivery. The adapter previously called the client's `nak()` with an options object when `requeue` was false. That method takes a delay in milliseconds, so the object became `NaN` and reached the wire as a null delay — an ordinary negative acknowledgement. A handler asking for the message NOT to be redelivered got it redelivered instead, up to `max_deliver` times, and only then did the message stop. `requeue: false` now maps to the operation that actually means it: `term()`. This brings the JetStream adapter in line with the contract `Message.nack(requeue?: boolean)` already describes and matches what the in-memory and Redis adapters do. Scope of the observable change: it is visible on every consumer. Under `ackMode: 'manual'` a handler calls `nack()` itself, so the difference is immediate. Under `ackMode: 'auto'` the adapter negatively acknowledges on a handler failure, and since consumers are now created with an explicit acknowledgement policy, the server tracks those acknowledgements rather than discarding them. (BREAKING, WI-195)
  - Migration: Any handler that called `message.nack()` or `message.nack(false)` and relied on the message coming back must now pass `message.nack(true)` explicitly. The retry it was relying on was accidental — the call said "do not redeliver" and the adapter redelivered anyway. Conversely, a handler that called `nack(false)` expecting the message to stop was previously getting `max_deliver` extra deliveries per message; that duplicate processing stops now, so any downstream de-duplication added to work around it can be reviewed. Terminated messages are removed from the consumer's pending set and are not sent to a dead-letter queue by the adapter. If you need failed payloads retained, publish them somewhere yourself before calling `nack(false)`.
- JetStream subscriptions now release what they hold. Three things change. Framework-generated ephemeral consumers are deleted on unsubscribe and disconnect. A subscription without a group gets a consumer nothing outside the process can address, and it used to be left on the server when the subscription ended — one more every restart, accumulating until an operator noticed and cleaned up by hand. Durable consumers are never deleted implicitly. A subscription with a group keeps its consumer through unsubscribe, disconnect and redeploy. That is deliberate: the framework unsubscribes every subscription on graceful shutdown, so deleting durables there would discard their position on each deploy and redeliver everything already acknowledged. Delete one when you mean to, with nats consumer rm. The pull loop is now stopped rather than merely flagged. Unsubscribing used to set a flag and leave the pull handle open, so the loop stayed parked and a restart timer kept re-entering it on a subscription that no longer existed. The handle is closed, the timer is cancelled, and the loop ends. Pausing no longer loses a message. A message already pulled when a subscription pauses or stops is now nak() ed and redelivered, instead of abandoned to sit in the acknowledgement window until ackWait expires. Pausing also no longer pulls batches it will not look at: the paused check happens before the fetch. (WI-196)
  - Migration: Nothing to do for new deployments. If earlier releases have been running for a while, the server may hold a backlog of orphaned ephemeral consumers — list them with `nats consumer ls <stream>` and remove the ones with generated `consumer-<uuid>` names; anything named `<group>--<subject>--<digest>` is a durable and must be left alone.
- A JetStream publish to a subject no stream binds now reports the real cause. The server answers such a publish with `jetstream is not enabled`, which names neither the subject nor the streams and sends operators looking for a JetStream that is disabled when it is not. The adapter now re-reports it with the context the server omits — the OneBun pattern, the resolved NATS subject, and every stream this application declares with its subjects — and preserves the original rejection as the error's `cause`. The misleading server text is not repeated inside the replacement message, so grepping a log for it no longer leads back to the wrong diagnosis. There is no pre-flight check against the locally declared `streams`: a subject may legitimately be bound by a stream another service owns, so the publish is always attempted and only the broker decides. (WI-197)
- JetStream streams are now reconciled instead of blindly rewritten, and three behaviours change. 1. Streams pre-provisioned out of band are no longer silently reset. The adapter used to send every stream key on every `connect()`, including `max_msgs`, `max_bytes` and `max_age` as explicit `undefined` when the application had not declared them. The client merges an update with a shallow `Object.assign`, so an explicit `undefined` overwrites the server's value — limits an operator had set were erased at every single startup. Only the keys the application actually declares are sent now; an undeclared key is absent from the payload rather than present-and-undefined. Separately, a stream whose storage type or retention policy conflicts with the declared configuration now fails startup with an error naming the field and the delete command, instead of the opaque `stream name already in use` the server produced after the adapter mistook an unrelated failure for a missing stream. 2. An application whose declaration would narrow a shared stream now fails to boot until the definitions are aligned. Previously the narrower declaration was applied, the stream stopped storing the subjects it no longer covered, and their messages were dropped with no error anywhere. The coverage check reads the server's own subject list and runs before the configuration hash is consulted, so a stale stamp left by an out-of-band `nats stream edit` cannot wave a narrowing declaration through. Widening a stream is still allowed. 3. The adapter stamps a configuration hash into stream metadata (`onebun.config-hash`, `onebun.prev-config-hash`, `onebun.reconciled-at`) and skips the update entirely when the configuration is unchanged — an unchanged declaration now performs no write at all, where it previously issued one update per stream per startup. Two processes writing different configurations for the same stream are detected as a reconcile cycle and fail startup rather than overwriting each other indefinitely. Because stream metadata requires nats-server 2.10 or newer, the JetStream adapter now requires that server version. A `streams.info` rejection is classified on the numeric API code and only a genuine not-found leads to a create; every other rejection, including a permissions denial or a transport timeout, is reported as itself. Every failure emits `onError` in addition to throwing. (BREAKING, WI-198)
  - Migration: Before upgrading, align stream declarations across every service that shares a stream. A declaration that covers fewer subjects than the stream already stores will now stop the application from booting instead of silently narrowing the stream — the error names each dropped subject. Check any stream whose `storage` or `retention` your application declares against what the server actually has. Those fields cannot be changed on an existing stream, so a mismatch now fails startup. Either align the declaration with the server, or delete the stream and let it be recreated — deleting discards every message it holds: `nats stream rm <stream>`. If you have been relying on the adapter to reset a stream's limits on startup, that no longer happens: limits set out of band now survive, because keys your application does not declare are never sent. Declare them explicitly if you want them enforced. The broker must be nats-server 2.10 or newer, which is what stores the stream metadata the reconciliation depends on.
- Unparseable and foreign JetStream messages are no longer silently destroyed, and consume-loop errors no longer disappear. A payload that failed to parse used to be acknowledged unconditionally, with no event, no log and no way to observe it. That acknowledgement is what destroyed it: the server considered the message handled and dropped it. It fired under `ackMode: 'manual'` too, where the whole point is that the adapter does not decide disposition on the operator's behalf, and it became outright destruction once consumers moved to explicit acknowledgements. The chosen disposition is `term()`: an unreadable message is terminated on the server and never redelivered, and the failure is emitted to `@OnQueueError` carrying the subject and the parse error. It is deliberately not left to `maxDeliver` — a payload that does not parse will not parse on a redelivery either, so retrying would only spend the acknowledgement window on a message that can never succeed. Valid JSON that is not a OneBun envelope gets the same treatment. It previously reached handlers with `data` set to `undefined`, which reads like an application bug rather than what it is: another producer publishing to a subject this application subscribes to. The parse branch is also no longer folded together with the handler call. An acknowledgement failure used to be caught by the parse handler and reported as a parse error, so the message was destroyed for a transport problem; it now surfaces to `@OnQueueError` as itself. Finally, errors from the consume loop reach `@OnQueueError` instead of being swallowed. A consumer that had failed was previously indistinguishable from one that was simply idle. (WI-201)
  - Migration: Register an `@OnQueueError` handler if you do not already have one — it is now the channel through which unreadable messages and consume-loop failures are reported, and `@onebun/nats` has no logger of its own. Expect to see errors that were previously invisible rather than new failures: nothing that used to work stops working. If a subject carries messages from a producer other than OneBun, those will now be reported and terminated instead of silently acknowledged — give that producer its own subject, or subscribe with a stream that does not bind it.
- A JetStream subscription whose consumer is deleted server-side now reports it and recovers, instead of stalling silently. Previously the subscription simply stopped receiving. The client does not fail when its consumer disappears — it retries the consumer lookup internally, forever — so the message loop parked and never woke, no event fired anywhere, and `isConnected()` kept reporting healthy. The first sign was usually a throughput alert hours later. The adapter now watches the consumer's notification channel. A deleted or missing consumer emits `@OnQueueError` and is re-created from the same configuration the subscription was built with — routed through the same code path that created it originally, so the acknowledgement policy, delivery policy, filter subject and in-flight limit cannot drift on recovery. Delivery resumes without restarting the application. One consequence cannot be engineered away and is worth planning for: deleting a consumer destroys its position on the server, so messages published while it was gone are not delivered to the re-created one. They remain in the stream, subject to its retention, but this subscription does not see them. No client can recover a position the server no longer has. `heartbeats_missed` and `stream_not_found` are reported to `@OnQueueError` as well, but deliberately not repaired — a missing stream is an operator problem, and re-creating a consumer against a stream that does not exist cannot help. (WI-202)
  - Migration: Register an `@OnQueueError` handler if you have not already: consumer deletion, missed heartbeats and a missing stream all surface through it, and none of them were observable before. If your operational runbook includes deleting JetStream consumers — to reset a position, for instance — be aware that the adapter now re-creates them automatically. Deleting one no longer stops a running application; it produces a gap in delivery instead. Stop the subscriber first if you need the consumer to stay deleted.
- **`unsubscribe()` and `disconnect()` now await in-flight handlers** (`@onebun/nats`) — a handler still running at shutdown was abandoned. Its `ack()` was then published onto a closing connection, where the client buffers it and drops it without raising anything: the handler completed, the server never heard about it, and the message was redelivered after `ackWait`. Because `QueueService.stop()` unsubscribes every subscription during graceful shutdown, this ran on every deploy, duplicating exactly the charge-and-email work the documentation recommends handlers for. `nc.drain()` does not help — it flushes subscriptions but never the application's loop body. Both calls now wait for the handler each subscription is executing, bounded by a fixed 30 seconds matching the default `ackWait`; past that point the server has already redelivered, so waiting longer cannot prevent the duplicate. `disconnect()` stops each subscription pulling before it waits, so no new handler starts during the drain. **Shutdown timing changes**: `unsubscribe()` and `disconnect()` now take as long as the slowest handler in flight, where they previously returned immediately. Keep handlers shorter than `ackWait`, or acknowledge early and track completion yourself. (WI-203)
- **`@Subscribe` patterns with named parameters and `#` wildcards now reach NATS as valid subjects** (`@onebun/nats`) — `@Subscribe('orders.{id}')` created a consumer filtering the literal subject `orders.{id}`, which matches nothing on the broker. Nothing errored: `consumers.add` succeeded, `isConnected()` reported healthy, and the subscription was simply, silently dead. A single translation now runs at every point where a OneBun pattern reaches the wire — the consumer filter, the publish subject, stream declarations, stream resolution and the core-NATS subscription: a `{name}` parameter becomes the NATS `*` wildcard, a trailing `#` becomes `>`, and `*` and literal tokens pass through. Handlers such as `@Subscribe('orders.{id}')` that never fired now fire. Translation only ever widens, and the in-process matcher built from the original pattern still narrows delivery back, so a subscription never receives more than its pattern matches. A stream declared `orders.{id}` binds `orders.*`; publishing is unaffected — `publish('orders.123', …)` still sends `orders.123`. A `#` in any position other than the final token now throws instead of producing an invalid subject: `#.created` used to ship `>.created`, which NATS accepts only at the end of a subject, and since the client does not validate subjects locally the broker rejected it asynchronously with nothing tying the failure back to the pattern. (BREAKING, WI-204)
  - Migration: A pattern with a `#` outside its final token (`#.created`, `events.#.created`) now throws where it is written — from the `JetStreamQueueAdapter` constructor for a stream declaration, so the application fails before `connect()`, and from the awaited `publish()`/`subscribe()` call otherwise. Use `*` to match a single token, or move the `#` to the end.
- **`Message.attempt` and `Message.maxAttempts` are populated on JetStream** (`@onebun/nats`) — both fields were declared on the message and never assigned, so they were permanently `undefined`. That made the retry recipe the documentation ships dead code: `if (message.attempt && message.attempt >= (message.maxAttempts || 3))` could never be true, so every failure fell through to `nack(true)` and kept being redelivered until `max_deliver` ran out. The documented terminal branch was unreachable. `attempt` now comes from the delivery count the server already tracks — 1-based, so the documented comparison works exactly as written — and `maxAttempts` is the `max_deliver` the subscription's consumer was actually created with, resolved once at subscribe time rather than recomputed per message: with reconciliation the server-side consumer is authoritative, and re-deriving the precedence chain in the consume loop could disagree with the consumer that really exists. Note that under `ackMode: 'none'` the server tracks nothing, so `attempt` stays 1 by design. On the memory, Redis and core-NATS adapters both fields remain `undefined` for now — nothing counts deliveries there. `NatsQueueAdapter` is not affected: it reports `supports('retry') === false`, so `undefined` is truthful. Aligning memory and Redis is tracked separately. (WI-205)
- **⚠️ A nacked message is reported as failed, not processed, on every adapter** — the documented way to write a handler is a `try`/`catch` whose `catch` calls `message.nack()`. Such a handler never throws, so nothing about its control flow distinguished it from a success: every adapter emitted `onMessageProcessed` for a message it had just dropped or requeued, and `onMessageFailed` fired only when a handler let an exception escape. A service written exactly as the documentation recommends therefore reported a failure rate of structurally zero while losing or retrying messages, and a message that took five attempts counted as five successes. Each adapter now reads the nack the message already recorded and emits `onMessageFailed` with a synthesised error naming it. The flag is read through an adapter-internal accessor (`NackAwareMessage` and `wasNacked()` in `@onebun/core`), so the public `Message` interface is unchanged and handlers cannot read it back. A handler that nacks and then throws still emits exactly one event, carrying the thrown error rather than the synthesised one, and `ack()`/`nack()` are first-call-wins everywhere. The rule does not vary with `ackMode`: `'none'` removes redelivery, not observability. **Migration:** anything counting `onMessageProcessed` as throughput, or alerting on `onMessageFailed`, will see both numbers move on upgrade — the processed count falls by exactly the messages the handlers were already rejecting and the failure count rises by the same amount, so re-baseline the alert rather than treating the step as an incident. Check too that an `@OnMessageFailed` handler tolerates an error it did not raise: the handler never threw, so the `Error` it receives is the framework's (`@onebun/core`, `@onebun/nats`) (WI-208)
- **⚠️ `nack(true)` under `ackMode: 'auto'` on JetStream actually redelivers now** — the consume loop's auto-acknowledgement ran on the raw JetStream message rather than through the framework's wrapper, so it bypassed the wrapper's own first-call-wins guard. A handler that called `message.nack(true)` sent `nak()`, returned, and then had `ack()` sent on the same message microseconds later, settling it and cancelling the redelivery it had just requested; `nack(false)` was terminated and then acked in the same way. Manual redelivery was therefore silently inoperative in the one mode where the framework acknowledges for you — the call succeeded, the server was told twice, and the last word won. The auto-acknowledgement is now skipped for a message the handler already dispositioned. `ackMode: 'manual'` was never affected, because it sends no automatic acknowledgement at all (`@onebun/nats`) (WI-208)
  - Migration: A handler that has been calling nack(true) under ackMode: 'auto' starts genuinely redelivering, up to max_deliver. If it was relying on the message quietly going away, give it a deadLetter queue or switch the call to nack(false).
- **⚠️ A handler with no parameter decorators no longer loses its exception filters** — the framework picks one of two execution paths per route, and a handler declaring no decorated parameters took an inline fast path that had no error handling at all. `throw new HttpException(404, 'gone')` from such a handler left the framework as a bare `500 Internal Server Error` in `text/plain`: the status, the message and the `{ success, error, code }` envelope were all lost, and `@UseFilters` on that route was dead code. The same throw from a handler that merely declared `@Query('q') q?: string` produced a correct `404 application/json`. Adding or removing a parameter decorator therefore silently changed a handler's error semantics, and nothing documented the link. Filters are now applied at every point that can throw while producing a route response — the handler on both paths, a guard whose `canActivate` throws, and an interceptor — so error handling no longer depends on a handler's signature. Guards and interceptors were previously unfiltered on **both** paths, not only the fast one. Filters are deliberately applied BELOW the middleware chain: `cors`, `security` and `rateLimit` set their headers after `await next()`, so catching higher up would have stripped those headers from every error response — error responses now carry them on both paths, where the fast path previously had none. A middleware that throws is still not filtered, for the same reason, and now produces a JSON envelope instead of `text/plain`. A guard returning `false` is unchanged and still yields the fixed `{success:false,error:'Forbidden',code:403}` without consulting filters, so a route-level filter cannot override that contract. Two smaller repairs ride along: an exception filter that itself throws, or returns something other than a `Response`, now falls back to the built-in default filter instead of escaping — applying filters on more paths widens the blast radius of a buggy filter — and an error carrying a non-numeric `code`, such as a socket failure's `ECONNREFUSED`, no longer crashes the default filter with a `RangeError` while building the response. The original value is preserved in `details.originalCode`. **Migration:** metrics and traces shift for previously-unfiltered errors. A fast-path error was recorded as a hardcoded 500; it is now recorded with the status the filter chose, so a handler throwing `HttpException(404)` moves from the 500 series to the 404 series — and under `httpEnvelope: true` the wire status is 200, so those errors record as successes. Re-baseline error-rate alerting on envelope-mode services. Fast-path throws also stop emitting a span `error` event, converging on how the other path already behaved (`@onebun/core`) (WI-222)
- **⚠️ A schema JSON Schema cannot fully express no longer collapses to a bare stub** — `getJsonSchema()` caught ArkType's conversion failure and returned `{ type: 'object', description: 'Schema validation is available but JSON Schema is not generated' }`. That is a structurally valid JSON Schema, so nothing downstream — an OpenAPI document, a form generator, a graph validator — could tell it from a schema for a genuinely unconstrained object, and the failure surfaced much later as "why is this form empty", with no log and no stack. It was not an edge case: ArkType has no JSON Schema representation for a `Date`, so any DTO carrying a timestamp was affected, along with every `.narrow()` predicate and `.pipe()` morph — eleven codes in all. Instead of catching the failure, the conversion now passes a fallback into ArkType, which keeps every node it could build and leaves only the unrepresentable one empty: `{ when: 'Date', name: 'string' }` yields the whole object with `name` typed, where it previously yielded `{ type: 'object' }` and nothing else. That ordering is forced rather than stylistic — the thrown `ToJsonSchemaError` carries the code but NOT the partially built schema, so a caught error can only ever produce a stub. A result that degraded carries the `x-onebun-partial` key (exported as `JSON_SCHEMA_PARTIAL`) listing the ArkType codes responsible, so a caller can detect it without string-matching a description; a schema that converts cleanly carries no marker at all, and the key is `x-` prefixed so OpenAPI tooling passes it through as a vendor extension. Both helpers now forward ArkType's own options — `fallback`, `dialect`, `target` — none of which were reachable before, so a caller wanting a lenient conversion had to bypass the package and call the method on the `Type` instance. A supplied `fallback` receives ArkType's real context, with the partially built schema in `ctx.base`, rather than the hardcoded `{ base: { type: 'object' } }` it used to get, and suppresses the marker for the codes it handles. `toJsonSchema()` still throws, so the strict helper and the best-effort one now differ only in what they do about an unrepresentable part (`@onebun/core`, `@onebun/docs`) (BREAKING, WI-224)
  - Migration: `getJsonSchema`/`toJsonSchema` now take ArkType's own option bag, so a caller passing the previous loosely-typed `{ fallback: (ctx) => ... }` gets a type error; ArkType's `fallback` is either an object keyed by code or a universal function, and both receive the real context. Anyone detecting the old stub by string-matching the description `Schema validation is available but JSON Schema is not generated` must switch to the `JSON_SCHEMA_PARTIAL` key — that description is gone.
- **PostgreSQL tables reach the PostgreSQL query builders** — every `pgTable` resolved to the SQLite builders across `select()`, `selectDistinct()`, `insert()`, `update()` and `delete()`. The queries ran correctly; the API was simply untypeable. `.limit()` after `.where()`, `.for('update', { skipLocked: true })` and a projected `.returning({ id: table.id })` were all unreachable, the last failing with `PgColumn is not assignable to SQLiteColumn`, and `select().from()` returned a hand-written `Promise & { where }` that ended the chain after a single call. The whole PostgreSQL surface is now typed: `.where()`, `.limit()`, `.offset()`, `.orderBy()`, `.for()`, `.$dynamic()` and projected `.returning()`, with `select().from()` returning drizzle's real `PgSelectBase`. SQLite tables are unaffected and still resolve to the SQLite builders. Worth knowing if you maintain code like this: the two dialects are not symmetrically distinguishable. `SQLiteTable<any>` and `PgTable<any>` each accept the other dialect's table, so overload ordering cannot separate them at all — but the BARE `PgTable` is dialect-branded and rejects a SQLite table, while the bare `SQLiteTable` does not reject a PostgreSQL one. `insert`/`update`/`delete` use the bare forms, so declaring PostgreSQL first is what fixes them; `select().from()` uses the `<any>` forms, where reordering would only have moved the defect onto SQLite, so it resolves through a conditional return type keyed on the `dialect` brand carried by the table's own columns. `getPostgreSQLDatabase()` and `getSQLiteDatabase()` are now documented as supported escape hatches rather than marked internal — they are no longer needed for ordinary queries, but remain the way to reach a dialect-only feature or a raw `sql` construction against the typed schema. The regression guard is a type-level test gated by `bun run typecheck`; a runtime test cannot observe this class of defect (`@onebun/drizzle`) (WI-225)
- Documentation correction: `docs/api/drizzle.md` and `docs/api/cache.md` presented two `forRoot()` calls as the way to run a main and an analytics database. It never worked. `forRoot()` stores its options on the module CLASS, which the whole process shares, and `DrizzleService` reads them late — so both calls settle before either service reads and every instance connects to whichever was evaluated LAST. Reproduced from the published example verbatim: two distinct `DrizzleService` instances, both on `main.db`, with no error. Anyone who followed it sent every analytics write into their production database. The same claim applied to `@onebun/cache`. Both pages now state what actually holds: `isGlobal: false` gives each importing module its own INSTANCE, all instances share ONE configuration, `forFeature()` does not hand back the root's instance, and multiple configured targets are unsupported for now — the boundary is the process, so a second application does not help either. (WI-230)
  - Migration: If you followed the documented multi-database or multi-cache pattern, audit the data: writes intended for the secondary target went to the primary one (or whichever configuration was evaluated last — it depends on module evaluation order, not on declaration order in your root module). No code change is required; the pattern never did what the page said.
- Guards now receive dependency injection and are resolved once at startup. They were the only element of the documented request pipeline with no DI: `executeHttpGuards` constructed each guard with `new guard()` and no arguments, on every request. A guard extending `BaseService` therefore saw `this.config` and `this.logger` as `undefined` inside `canActivate`, so the documented `this.config.get('auth.apiKey')` example threw a `TypeError` at request time, and constructor dependencies were never injected. Guards are now resolved through the module that owns the controller, exactly as interceptors already were. An instance passed directly — `@UseGuards(new RolesGuard(['admin']))` — keeps working unchanged. (WI-231)
- WebSocket gateways can authenticate a client, and the built-in `WsAuthGuard` can now pass. Previously the framework parsed the bearer token and then created every client with `authenticated: false`, and nothing anywhere set it to `true` — so `WsAuthGuard`, an exported and documented guard, denied every client forever, and `WsPermissionGuard` checked a permission list nobody populated. A handler guarded with either was unreachable. `@WebSocketGateway({ authenticate })` now runs during the upgrade and decides who the client is, with three outcomes: `false` refuses the upgrade with HTTP 401, `null` admits the client as anonymous so authentication guards still deny it, and `true` or an object admits it as authenticated with the identity the guards read. Omitting the option keeps the previous behaviour. (WI-234)
  - Migration: If you worked around this by setting `client.auth.authenticated` in an `@OnConnect` handler, that still works — `authenticate` is the supported way now, and it runs before the connection is accepted rather than after. No change is required for gateways that do not use `WsAuthGuard` or `WsPermissionGuard`.
- `DrizzleService` and `CacheService` now close their connections when the application stops. Both had a `close()` method and nothing in the lifecycle called it, so a service built by one test suite kept its connection open into the next — the direct mechanism behind a suite failing with `database "..." does not exist` after an earlier suite dropped its throwaway database. Both now implement `OnModuleDestroy`. A SHARED Redis client is deliberately not disconnected by the cache hook: `close()` disconnects only a client the service owns, and the application already disconnects a shared one during `stop()`, gated on `closeSharedRedis` — so `stop({ closeSharedRedis: false })` still leaves it connected for the rest of the process. (WI-236)
- `DrizzleModule.forRoot({ isGlobal: false })` no longer de-globalizes the module permanently. The global-module registry is process-wide and the removal had no counterpart, so one opt-out anywhere latched the module non-global for the rest of the process — including for later `forRoot()` calls that asked for the default. A later unnamed `forRoot()` that does not opt out now puts the module back. Note what this is and is not: the registry still holds one entry per module class for the whole process, so the last unnamed `forRoot()` evaluated anywhere decides globality for every application in that process. Use `forRoot({ as: TOKEN })` when two configurations must not interfere — a named registration never touches the registry. The same applies to `CacheModule`. (WI-237)
- The shared Redis client is reference-counted, and a broken cache no longer looks like an empty one. Previously the FIRST application to stop disconnected the shared client outright — `stopAll()` stops each sub-application with the default `closeSharedRedis: true` — so in multi-service mode every sibling still serving traffic lost its connection and was never told: measured, a surviving consumer's cache read returned `undefined` rather than failing. Each consumer now takes a hold when it first obtains the client and `app.stop()` releases it; the connection closes when the last hold goes. On top of that, `RedisCache` re-acquires a shared client that went away instead of reporting a miss, and THROWS when it cannot. `isConnected()` now delegates to the driver's live flag — it used to report `true` after the server had gone, because the flag was set once at connect and never updated. (BREAKING, WI-238)
  - Migration: `RedisCache.get()`, `delete()` and `has()` now throw on an operational failure instead of returning `undefined`/`false`. A genuinely absent key still returns `undefined` — that distinction is the point. Code that relied on a Redis outage silently degrading to cache misses will now see errors; that is deliberate, because anything treating a miss as "not present" (rate limiting, replay guards, locks) was reaching the wrong conclusion. The re-acquire is bounded by a short deadline rather than waiting on the driver's indefinite auto-reconnect.
- Two provider classes that share a name no longer make startup depend on the order of the `providers` array. The dependency-ordering pass keyed its bookkeeping by class NAME, so creating one class marked a different class of the same name as created; the deferral was skipped and boot died with `Could not resolve dependency X for service Y. Ensure X is decorated with @Service() and listed in a module's providers` — for a class that was both. `providers: [Alpha, Beta, Gamma]` threw while `providers: [Gamma, Beta, Alpha]` booted, same classes and same graph. The pass is now keyed by class identity. (WI-241)
- SQLite: `.get()` on a join between tables that share a column name no longer returns a scrambled row. The single-row fast path read the row as an OBJECT and handed it to drizzle's positional mapper — an object has one key per name, so two tables both selecting `id` produced a row one value short and every field after the collision shifted: an order's `total` came back holding a user id, and the last column vanished. HTTP 200 throughout, and a row like that written back corrupts the database. Such queries now take drizzle's own array-shaped read; queries without a name collision keep the fast path, which is measured at 345us against upstream's 1373us for `select().from(t).get()` over 5000 rows. (WI-256)
- Shutdown now waits for the requests it is serving. The Promise from `server.stop()` was discarded, so destroy hooks ran under live traffic and `process.exit(0)` then severed whatever was mid-response — every deploy cut requests that were in flight. The sequence now refuses new work with a 503 while the listener stays open, waits for in-flight requests to finish, and only then closes and runs the destroy hooks. `stop()` is idempotent and a second signal no longer re-runs every hook — measured before the fix, one `docker stop` ran each destroy hook twice. In multi-service mode a single parent handler stops every service concurrently: previously each child registered its own handler ending in `process.exit(0)`, so the first service to finish killed the process and truncated its siblings' teardown, and the orchestrator's ordered `stopAll()` never ran on a signal at all. (WI-258)
  - Migration: `shutdownTimeout` (default 15s) bounds the whole sequence; the process exits with a non-zero code and a log line naming what was still running if it expires. In multi-service mode, child applications no longer install their own signal handlers — the parent stops them all. If you called `stop()` from a `beforeApplicationDestroy` hook expecting the server to still serve, note that the listener is now already refusing new requests at that point.
- SQLite `transaction()` now rolls back. It never did: drizzle's bun-sqlite session is synchronous, so `client.transaction(fn)` committed the moment the callback returned — which for an `async` callback is its first `await`. A throw after that point propagated to the caller while every row it had written stayed committed, in the one operation transactions are taken for. The transaction is now issued as an explicit BEGIN/COMMIT/ROLLBACK and held across awaits. Because SQLite has a single connection, queries issued elsewhere in the application while a transaction is open are QUEUED and run after it commits or rolls back, instead of silently joining it and being undone with it — a concurrent write no longer disappears because an unrelated transaction failed. A query issued through `DrizzleService` from INSIDE the callback (a repository method, say) runs on that transaction and is rolled back with it, so repositories work inside a transaction without being rewritten. Two overlapping transactions are serialized. PostgreSQL is unchanged. (WI-268)
  - Migration: Code that relied on a SQLite transaction NOT rolling back was relying on a defect. Two behaviours are new and may need attention: a nested `transaction()` inside a callback now throws `DrizzleTransactionError` with code `SQLITE_TRANSACTION_NESTED` (do the work through the outer `tx`), and a synchronous `.get()`/`.all()`/`.run()`/`.values()` issued by a CONCURRENT caller while a transaction is open throws `SQLITE_TRANSACTION_SYNC_QUERY` — await the query instead, and it will be queued. Raw escape hatches (`getSQLiteClient()`, `getSQLiteDatabase()`, prepared statements) are not gated and still join an open transaction.
- `@All()` works. A single `@All()` route anywhere in the application used to abort startup with a raw Bun `TypeError` — not just that route, the whole process, so every other route died with it. The decorator is exported, documented without caveat, and the NestJS migration guide lists it as behaving the same. A path carrying `@All()` is now served by a dispatcher that answers ANY method, including verbs outside the `HttpMethod` enum: PROPFIND, PURGE, LOCK and QUERY all reach the handler with route parameters intact, which is what a reverse proxy or a webhook shim needs. An explicitly declared route on the same path wins for its own verb regardless of declaration order, so `@Get('/x')` alongside `@All('/x')` sends GET to the `@Get` handler. Metrics and trace spans for such a route now record the request's real method instead of the literal `ALL`. (WI-277)
- An empty environment variable now means "not configured" rather than a value. `DB_HOST=` — the shape a blank docker-compose entry or an unfilled ConfigMap key produces — used to override the declared `default` and satisfy `required: true`, so an application booted against an empty host instead of failing with something readable; an unset variable with neither default nor requirement became `''`, `0` or `false`. Separately, environment values are no longer printed in validation errors at all: a variable marked `sensitive: true` was written to the log in cleartext by the framework's own startup error, exactly when logs get read, and nothing a user could write suppressed it. Errors now describe the value instead of quoting it, for every variable rather than only the ones somebody remembered to mark. (WI-298)
  - Migration: If you deliberately set a variable to an empty string to mean "empty value", that now resolves to the declared default and does not satisfy `required: true`. The error text distinguishes "is set to an empty string" from "is not set", so which one happened is visible in the log.
- `createHttpClient` no longer replays non-idempotent requests. Every method was retried by default, so an unconfigured POST or PATCH was sent up to four times on 408/429/500/502/503/504 or on a timeout — a charge taken four times, an order placed four times, with nothing in the caller's code asking for it. Retries now apply to the idempotent set (`GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`) unless `retries.methods` says otherwise. Transport failures are also classified separately instead of being reported as a 500: a refused connection or DNS failure is retried for idempotent methods (`retryOnNetworkError`, default on), while a timeout is NOT retried by default (`retryOnTimeout`, default off) because the server may have processed the request. `retryOn` stays a pure list of status codes. (WI-304)
  - Migration: A caller who wants a non-idempotent method retried lists it: `createHttpClient({ retries: { methods: ['GET', 'HEAD', 'OPTIONS', 'PUT', 'DELETE', 'POST'] } })`. `retries` also accepts a partial object now — overriding `max` alone keeps the documented defaults for everything else, which previously did not typecheck.
- Documentation corrected against actual behaviour across the whole tree. Notably: the drizzle Testing section called `onAsyncInit()`, a hook renamed to `onModuleInit` six months ago, so the documented test recipe threw on its first line; and a dialect-neutral sentence claimed a service query inside a transaction callback never joins the transaction, which is true on PostgreSQL and false on SQLite — the page said so 15 lines from the section that said the opposite. Also corrected: hook ordering on every page that listed destroy hooks before the HTTP listener closes, the retry defaults, the rate-limit key and `trustProxy`, `@UseGuards` across transports, `getService()`/`getLayer()` refusing an ambiguous tag, the environment-value redaction promise now covering every variable rather than only the ones marked `sensitive`, and a `BaseRepository` example that did not typecheck. (WI-309)

### Security

- Authorization bypass: a route-level `@UseGuards(...)` written ABOVE the HTTP method decorator was silently discarded, so a route that looked guarded was reachable and the handler ran. `@UseGuards(DenyGuard)` above `@Delete('/:id')` answered HTTP 200; the same guard below it answered 403. `@UseInterceptors` and `@UseFilters` were skipped the same way. Controller-level decorators were unaffected, which is why the defect was invisible to anyone testing only class-level guards. Cause: the route decorator snapshotted pipeline metadata when it ran, and TypeScript applies method decorators bottom-up, so anything written above the method decorator executed after the snapshot. Decorator source order no longer changes runtime behaviour at either level. (WI-231)
  - Migration: Affects @onebun/core 0.4.4 and earlier. Audit every route-level `@UseGuards`, `@UseInterceptors` and `@UseFilters` in your codebase: any written above the `@Get`/`@Post`/`@Delete` decorator were not running. The documentation used exactly that order in all of its route-level examples, so code copied from the docs is affected. No source change is required after upgrading — both orders now work — but routes that were unguarded in production should be treated as having been exposed.
- Authorization bypass: a class-level `@UseGuards` on a base controller was not inherited by controllers extending it, so the subclass answered as if unprotected — HTTP 200 with the handler reached, no error and nothing in the logs. `@UseMiddleware`, `@UseInterceptors` and `@UseFilters` were dropped the same way. The shape affected is the ordinary one: a shared `ProtectedBase` carrying the decorator once, which feature controllers extend. Cause: the metadata polyfill is a `WeakMap` lookup on the exact class with no prototype-chain walk, unlike the `reflect-metadata` it replaced. All four class-level decorators now inherit, base entries first and then the subclass's own — the same order in which controller-level and route-level entries already merge. Routes declared on a base class are still not mounted under the subclass; that is unchanged and fails closed with a 404. (WI-235)
  - Migration: Affects @onebun/core 0.4.4 and earlier, and is separate from the route-level decorator-ordering bypass fixed in the same release — an audit for one will not find the other. If you use a shared protected base controller, treat every subclass route as having been exposed. No source change is required after upgrading; if a subclass was relying on NOT inheriting its base's guards, it will now be guarded.
- `@UseGuards` now runs on WebSocket and queue handlers. It was silently ignored there — no type error, no warning — while the NestJS migration guide states it "works identically on HTTP routes, WebSocket message handlers, and queue consumers". Anyone following that guide shipped an unguarded consumer that looked guarded. One decorator and one metadata key now cover all three transports, the way `@UseInterceptors` already did. Guards on WebSocket and queue also get dependency injection from the same resolver as HTTP: a guard with a constructor dependency, or one extending `BaseService`, previously threw on every message and the message was dropped with nothing logged, because it was constructed with a bare `new`. Unresolvable dependencies now fail at startup rather than per message. `MessageGuardConstructor` was typed so that a guard taking any constructor argument was a type error — the exact shape DI exists for — and that is fixed too. (WI-285)
  - Migration: A guard that reaches for HTTP accessors now denies on WebSocket and queue instead of throwing — narrow with `isHttpContext`/`isWsContext`/`isQueueContext` if one guard serves several transports. A denied queue message is `nack`ed without redelivery, so it dead-letters where the adapter has a DLQ and raises `onMessageFailed`; a denied WebSocket message answers `{ event: 'error', data: { code: 'FORBIDDEN' } }` on the pending ack and leaves the socket open.
- Request and response validation no longer fails OPEN when a second physical copy of `arktype` is installed. Success was decided with `result instanceof type.errors` against the copy inside `@onebun/core`, so a failure produced by another copy was not recognised, fell through the success branch, and was returned as the validated value — the handler received the error array and the response wrapper serialised it, answering HTTP 200 with ArkType error objects as the payload. The same identity check made every `@Body` infer as optional. Detection is now structural, using ArkType's own brand, so it holds across copies; an unrecognisable result raises a framework error naming the duplicate-copy cause instead of being passed through as data; and a duplicated installation is reported once at startup, detected through ArkType's own `$ark2` registry marker. `arktype` stays a regular dependency of `@onebun/core` — making it a peer would break `@onebun/drizzle`, which carries its own copy. (WI-288)
- Rate limiting now identifies callers by their transport peer address, and `X-Forwarded-For` is only trusted when the application says a proxy is in front of it (`trustProxy`, default off). Both halves were exploitable: with no proxy every caller shared one `unknown` bucket, so a single client exhausted the limit for everybody; and because the forwarded header was trusted unconditionally, rotating it removed the limit entirely — measured, 10 requests against `max: 3` all returned 200. With the fix the same run returns 429 from the fourth request, and with `trustProxy: true` the forwarded client is the bucket, which is what an operator behind a real proxy wants. The same resolution now feeds the trace `remoteAddr` field, so the limiter and the traces no longer disagree about who called. (WI-297)
  - Migration: If your application runs behind a load balancer or CDN and relies on `X-Forwarded-For`, set `trustProxy: true` in `ApplicationOptions`. Leave it off when the process is reachable directly, or a caller can pick their own rate-limit bucket by setting a header. `getClientAddress(req)` and `getPeerAddress(req)` are exported for custom key generators.

### Breaking Changes

- **⚠️ The shared Redis client is reference-counted, and a broken cache no longer looks like an empty one** — `SharedRedisProvider` connects lazily and had no ownership tracking, while `disconnect()` tore the singleton down unconditionally. `stopAll()` stops each sub-application with the default `closeSharedRedis: true`, so in multi-service mode the FIRST one to stop disconnected the client for every sibling still serving traffic — and the siblings were never told: measured, a surviving consumer's cache read returned `undefined`, making a dead connection indistinguishable from an absent key. Each consumer now takes a hold when it first obtains the client, `app.stop()` releases it, and the connection closes when the last hold goes. `RedisCache` re-acquires a shared client that went away rather than reporting a miss, and THROWS when it cannot; the re-acquire is bounded by a short deadline, because the driver's auto-reconnect never rejects on its own — measured, a connect to a refused port stays pending indefinitely. `RedisClient.isConnected()` now delegates to the driver's live flag; it used to report `true` after the server had gone, because the flag was set once at connect and never updated. **Migration:** `get()`, `delete()` and `has()` now throw on an operational failure instead of returning `undefined`/`false`, while a genuinely absent key still returns `undefined` — that distinction is the whole point, since anything treating a miss as "not present" (rate limiting, replay guards, locks) was reaching the wrong conclusion (`@onebun/core`, `@onebun/cache`)
- **⚠️ A module is constructed once per application, so `forFeature()` shares instead of duplicating** — the documented remedy for a non-global dynamic module is that each submodule imports it via `forFeature()`. It did not share, it duplicated: measured with the real `CacheModule`, a root plus two leaves produced THREE `CacheService` instances, three initializations, and a value written through one was invisible through another. For `DrizzleModule` that is three connection pools. Deduplication existed only for `@Global()` modules; a non-global one was reconstructed for every importer. A module class is now built exactly once per application and `imports` decides VISIBILITY only, which makes the two modes an honest pair — `@Global()` reaches every module without an import, non-global reaches only modules that import it, and either way there is one instance. **Migration:** a module's `onModuleInit`/`onModuleDestroy` now run once rather than once per importer, so a suite counting hook invocations will see different numbers; and anything relying on `isGlobal: false` for a fresh instance per importer now gets one shared instance — that was never a working multi-database mechanism, since every instance read the same last-written configuration anyway (`@onebun/core`)
- **⚠️ JetStream consumers are created with explicit acknowledgements** — consumers are now created with `ack_policy: explicit` for both `ackMode: 'auto'` and `ackMode: 'manual'`. Previously anything other than `'manual'` produced `ack_policy: none`, under which the server tracks no acknowledgements at all: `max_ack_pending`, `ack_wait`, `max_deliver`, `message.ack()`, `message.nack()`, retries and the dead-letter queue were all inert while the documentation advertised them, and a handler that threw was never redelivered. `ackMode` now selects only *who* acknowledges — the adapter on the handler's behalf, or the handler itself — never whether the server tracks acknowledgements. **Migration:** durable consumers created by earlier releases carry a non-explicit ack policy, and `ack_policy` cannot be changed on an existing consumer, so they must be deleted and recreated: `nats consumer rm <stream> <consumer>`. `subscribe()` detects such a consumer on startup and refuses to start, naming the stream, the consumer and the exact command in the error (`@onebun/nats`)
- **⚠️ `subscribe()` rejects on consumer setup failures** — consumer creation used to blind-add inside a bare `catch {}`, so an authentication denial, a disabled JetStream or a transport timeout was indistinguishable from "the consumer does not exist". `subscribe()` now probes `consumers.info` first and classifies the rejection by its numeric API code: only `ConsumerNotFound` leads to a create, and every other rejection — including a genuine `consumers.add` failure — is rethrown as itself and emitted to `onError` rather than swallowed. An ephemeral subscription that collides with an existing consumer is also rejected instead of hijacking it. An application whose consumers cannot be reconciled now fails to boot instead of running degraded (`@onebun/nats`)
- **⚠️ Conflicting `group` configuration fails fast** — OneBun stamps a hash of the applied consumer configuration onto the consumer's metadata, so a consumer that already matches is left untouched (no `consumers.update` call at all) and a changed configuration is applied with every pre-existing metadata key carried forward. Two services that share a `group` but pass different `consumerConfig` or `retry` options no longer silently overwrite each other's consumer: the second writer sees the hash it just applied already replaced and fails with a reconcile-cycle error naming the diverging fields. Align `consumerConfig`, `prefetch` and `retry.attempts` across the services, or delete the consumer. The stamp uses the `onebun.config-hash`, `onebun.prev-config-hash` and `onebun.reconciled-at` metadata keys, which require nats-server 2.10 or newer (`@onebun/nats`)
- **⚠️ Durable consumers are named per group *and* pattern** — a durable consumer is now named `${group}--${filterSubject}--${digest}` — the sanitised group and subject plus a short digest of the raw pair, since sanitisation alone aliases `orders.*` with `orders.>` — with every character outside `[-\w]` replaced by an underscore, and is no longer the bare group name. Two subscriptions that shared a `group` but filtered different subjects used to collide on one consumer — the second silently took the first's over, so one subject received everything and the other received nothing. They are two consumers now. The same group with the same pattern still resolves to a single durable, which is what lets several instances of a service share the work, so load balancing is unchanged. A subscription without a `group` remains ephemeral and is now named `consumer-<uuid>` from `crypto.randomUUID()` rather than from the millisecond clock, so two of them created in the same millisecond can no longer land on the same name. Consumer identity is not part of the hashed configuration: two subscriptions differing only in `group` carry different durable names but the same config hash. **Migration:** consumers created by the previous release are orphaned by the rename and must be deleted with `nats consumer rm <stream> <consumer>` — OneBun creates the replacements under the new names on the next boot (`@onebun/nats`)
- **⚠️ Consumers are created with `deliver_policy new`** — the delivery policy is now set explicitly on creation instead of being left to whatever the server defaults to. On a stream that retains messages this means a newly created consumer starts from the moment it subscribes: unconsumed messages already in the stream are skipped once on upgrade instead of replaying into handlers. Like `ack_policy`, `durable_name` and `name`, the delivery policy is immutable on an existing consumer, so it is sent on the create path only — the reconciler's update path carries just `ack_wait`, `filter_subject`, `max_ack_pending`, `max_deliver` and `metadata` (`@onebun/nats`)
- **⚠️ A configured queue adapter now enables the queue** — an application that sets `queue.adapter`, `queue.options` or `queue.redis` without `queue.enabled` now constructs and connects that adapter during `app.start()`. Previously the queue was enabled only by a queue decorator on a controller or an explicit `queue.enabled: true`, so a producer-only application booted with the queue silently disabled and every `publish()` was discarded. Such an application will now fail to boot if the broker is unreachable, where it previously started and dropped messages. `queue.enabled: false` alongside an adapter configuration keeps the queue disabled and logs one warning naming the contradiction — it is not an error. The multi-service orchestrator resolves the decision once and passes it to every child. `QUEUE_NOT_ENABLED_ERROR_MESSAGE` was rewritten, so code matching that literal must be updated; code comparing against the exported constant is unaffected (`@onebun/core`)
- **⚠️ Streams pre-provisioned out of band are no longer reset on connect** — the adapter used to send every stream key on every connect, including `max_msgs`, `max_bytes` and `max_age` as an explicit `undefined` when the application had never declared them. The client merges an update with a shallow `Object.assign`, so an explicit `undefined` overwrites whatever the server held: the limits an operator had set were erased at every single startup. The update payload now carries only the keys the application actually declared, and an undeclared key is absent rather than present-and-undefined. `retention`, `storage` and the `num_replicas` default are applied on the create path only — `update` cannot change the first two, and applying a default on update would rewrite a value the application never asked about; a declared `streamDefaults` counts as declared and still reaches both paths. A stream whose storage type or retention policy conflicts with the declared configuration now fails startup with an error naming the field and `nats stream rm`, in place of the opaque `stream name already in use` the server produced when a probe failure was misread as absence. That probe is classified by its numeric API code now: only `StreamNotFound` leads to a create, and a permissions denial or a transport timeout is rethrown as itself (`@onebun/nats`)
- **⚠️ A declaration that would narrow a shared stream fails startup** — subject coverage is checked against the server's own subject list before anything else: if the declaration would no longer cover a subject the stream already stores, startup fails and the error names every dropped subject. Widening the declaration is still allowed. An application narrowing a shared stream now fails to boot until the definitions are aligned across the services, instead of quietly dropping the subjects it stopped covering. The check runs before the configuration hash is compared, so a stale stamp left by an out-of-band `nats stream edit` cannot wave the narrowed declaration through (`@onebun/nats`)

- **⚠️ The JetStream dead-letter queue is implemented, so `deadLetter` stops being inert** — `supports('dead-letter-queue')` returned `true` while `SubscribeOptions.deadLetter` was read nowhere in the adapter: `queue` was ignored outright and `maxRetries` was ignored twice over, so a repeatedly failing message was simply left for the server to exhaust and the dead-letter stream stayed permanently empty. Two behaviours change for anyone who already sets `deadLetter`. First, `maxRetries` now participates in the consumer's `max_deliver`, resolved as `retry.attempts` → `deadLetter.maxRetries` → `consumerConfig.maxDeliver` → `3` — `retry.attempts` stays ahead of it so configurations written before this release keep the exact `max_deliver` they had, but a consumer configured only through `deadLetter.maxRetries` is reconciled to the new value on the next startup. Second, the delivery the server would otherwise have made the last is now republished to `deadLetter.queue` and the original is terminated, instead of being redelivered until `max_deliver` runs out. The same routing applies to `message.nack(false)` and the bare `message.nack()` under `ackMode: 'manual'`; `nack(true)` still asks for redelivery. The copy is published **before** the original is terminated — a failed republish leaves the message exactly as it was and reports the failure to `@OnQueueError`, because losing the payload is the one outcome a dead-letter queue exists to prevent. It keeps the original `id` and gains `dlq.originalPattern`, `dlq.deliveryCount` and `dlq.error` in its metadata. **Migration:** `deadLetter.queue` must be a literal subject bound by a declared stream — a wildcard, or a queue equal to the subscription's own pattern, now throws from `subscribe()` at startup rather than failing on the first dead letter (`@onebun/nats`)
- **⚠️ A `#` outside the final token of a pattern now throws** — `#` translates to the NATS `>` wildcard, which NATS accepts only at the end of a subject, so a pattern such as `#.created` used to ship the syntactically invalid subject `>.created`. The client does not validate subjects locally, so the broker rejected it asynchronously, long after the call that produced it and with nothing tying the failure back to the pattern. Such a pattern now throws where it is written: from the `JetStreamQueueAdapter` constructor for a stream declaration, so the application fails before `connect()`, and from the awaited `publish()` or `subscribe()` call otherwise. The error names the offending pattern and the final-token rule. Use `*` to match a single token, or move the `#` to the end (`@onebun/nats`)

- **⚠️ `@Global()` services are scoped per application, not per process** — a `@Global()` module's service instances, the record of which global modules have been constructed, and the options a dynamic module was imported with all used to live on `globalThis`, so one process held exactly one copy no matter how many applications ran in it. A second `DrizzleModule.forRoot()` or `CacheModule.forRoot()` therefore reused the first application's connection instead of opening its own — a test suite could talk to, and drop, the wrong database. Each application now owns a `GlobalScope` threaded by reference through its whole module tree, and disposes it on `stop()`; in multi-service mode the boundary is the sub-application, so stopping one leaves its siblings untouched. Dynamic-module options are captured at import time, so a later `forRoot()` in the same process cannot retroactively change what an already-running application is using. **Migration:** code that relied on one application's instance leaking into a later application in the same process now sees a fresh instance — this mostly affects test suites that booted several applications and expected shared state; assert on each application's own `getService()` result (`@onebun/core`)
- **⚠️ `exports: [SomeModule]` throws instead of silently doing nothing** — the NestJS module re-export idiom was discarded without a trace: `getServiceTag()` throws for a module class and `getExportedServices()` swallowed the throw, so a re-exported module contributed nothing to its importer. It now throws `OneBunInvalidExportError` naming both modules. **Migration:** the entry was always a no-op, so nothing that relied on it was working — an importer either failed at a controller with no mention of the export, or also imported the module directly and got a second copy of every provider (two `DrizzleService`s, two connection pools). Remove the module from `exports` and import the providing module directly wherever its services are needed (`@onebun/core`)
- **⚠️ `TestingModule.overrideProvider()` reaches services and imported modules** — the override was applied by patching the root module after the whole tree had been built, so it reached root-module controllers only. A service that injected the overridden class, or anything inside an imported module, was **silently ignored**: the mock was accepted and then bypassed with no warning and no error, which is the failure mode that lets a real DI bug ship green. Overrides are now seeded into every module before any provider is constructed, and the real provider is not constructed at all when one replaces it — so a `.useClass()` mock's lifecycle hooks fire exactly once instead of once per module. **Migration:** a test that passed because its mock was ignored will start seeing the mock; tests that hand-wired around the old behaviour can drop the workaround (`@onebun/core`)

### Deprecated

- **`clearGlobalServicesRegistry()` and `getGlobalServicesRegistry()`** — both now operate only on the process-default scope used by a direct `new OneBunModule(...)`, never on an application's own scope, so they can no longer observe or reset what a running application holds. `getGlobalServicesRegistry()` has always returned a copy, so an assertion against it could not have detected a change anyway. Assert on resolved instances — `app.getService(Class)` — instead (`@onebun/core`)

### New Features

- **`deleteDurableConsumer()` on the JetStream adapter, and a documented consumer lifecycle** — `unsubscribe()` and `disconnect()` deliberately never remove a durable consumer (they run on every graceful shutdown, and deleting there would discard its position on each deploy), which left no supported way to decommission one at all. `(queueService.getAdapter() as JetStreamQueueAdapter).deleteDurableConsumer(pattern, group)` does it: `true` when a consumer was removed, `false` when there was none, so it is safe to call twice, and a permissions denial is rethrown rather than reported as "already gone". Stream resolution is strict on this path — an unbound pattern throws and names every declared stream instead of falling back to the first one the way `publish()` and `subscribe()` do, because a typo must not delete a consumer on an unrelated stream. The docs now also state what `group` actually is: on JetStream a PERMANENT server resource named from the group and pattern together, so templating it per run or deploy orphans a consumer every time — name the role, not the deployment; on `NatsQueueAdapter` the same option is a stateless queue group that dies with its members (`@onebun/nats`)
- **⚠️ `PublishOptions.messageId` now enables JetStream deduplication, and `StreamDefinition.duplicateWindow` sets the window** — `messageId` was an inert echo: it reached the message body and came back as `Message.id`, but JetStream keys deduplication strictly off the `Nats-Msg-Id` header, which was never sent. Publishing the same logical message twice stored it twice, so an outbox could not be replayed safely. A caller-supplied `messageId` is now sent as `Nats-Msg-Id` and the server drops a second message carrying an id it has already seen inside the stream's deduplication window. Only a supplied id enables it — omitted or empty, the adapter generates one, uses it as `Message.id` and sends no header, because a generated id is unique per call and would only grow the server's deduplication index. The id still travels in the JSON body, so the wire format is unchanged and existing consumers are unaffected; on the memory, Redis and core-NATS adapters `messageId` remains an echo. `duplicateWindow` (nanoseconds, matching `maxAge`) sets the window per stream and is inherited from `streamDefaults`; omitted, the server's own two-minute default applies. It is sent only when declared, on both the create and the update path, so a window an operator set out of band is never reset by a deploy. **Migration:** a `messageId` reused within the window is now silently rejected — the second message is not stored while `publish()` still resolves with no error and no local signal. Audit any caller passing `messageId` and make sure it is unique per logical message, or drop the option (`@onebun/nats`)
- **`ackMode: 'none'` for fire-and-forget delivery** — `SubscribeOptions.ackMode` accepts a third value alongside `'auto'` and `'manual'`. Under `'none'` a message is delivered exactly once and nothing is acknowledged, so there is no redelivery and no dead-letter routing on any adapter — the mode to choose when losing a message costs less than processing it twice. Everything that depends on the broker tracking delivery state goes inert with it: `retry` (including `retry.attempts`), `deadLetter`, `ack_wait`, `max_deliver`, and the `attempt`, `maxAttempts` and `redelivered` fields on `Message`. A handler that throws still emits `onMessageFailed`, so failures remain observable; the message is simply not retried, and `message.ack()`/`message.nack()` become no-ops on every adapter — on JetStream they are recorded so the subscription still reports the right lifecycle event, but nothing reaches a server that is tracking nothing, so no ack, nak or term is sent and a configured `deadLetter` is not routed to. JetStream creates the consumer with `ack_policy: none` and omits `ack_wait`, `max_deliver` and `max_ack_pending` from the wire entirely — the server accepts them but ignores them, and sending them would record a redelivery policy that cannot occur. Redis skips both the requeue and the dead-letter branch; the in-memory adapter suppresses `nack(true)`, which would otherwise resurrect a message in the one mode that promises a single delivery; `NatsQueueAdapter` gains nothing on the wire, because core NATS never had an acknowledgement protocol, so `'none'` is simply the only mode that describes it truthfully. `'auto'` and `'manual'` are unchanged and existing code needs no edits. One constraint follows from JetStream itself: `ack_policy` is fixed when a consumer is created, so a durable that already exists under one mode cannot be moved between `'none'` and the other two — startup fails naming both policies, and the fix is `nats consumer rm` on that durable (`@onebun/core`, `@onebun/nats`)
- **`ackTimeout` on `@Subscribe` — an acknowledgement deadline per subscription** — `SubscribeOptions.ackTimeout` sets how long the server waits for an acknowledgement before it redelivers, for one subscription. The only knob before was `consumerConfig.ackWait`, which applies to every consumer the application creates, so a handler that takes minutes and one that takes milliseconds had to share a window sized for whichever mattered more. Each side of the boundary keeps its own unit — ackTimeout is in milliseconds; consumerConfig.ackWait is in nanoseconds — and the adapter multiplies by 1_000_000 on the way to the wire. JetStream resolves the consumer's `ack_wait` as `ackTimeout -> consumerConfig.ackWait -> DEFAULT_ACK_WAIT_NANOSECONDS` (30 seconds), so an application that sets neither is unaffected. Because `ack_wait` is one of the fields the reconciliation stamp hashes, a changed value is applied to an existing durable consumer automatically on the next start — no `nats consumer rm` in between — and the consumer's name is unchanged, since a timeout is configuration and not identity. Two processes that disagree on it still fail startup with a reconcile-cycle error, which now reports each diverging field with both values (`ack_wait (this process 45000000000, on server 30000000000)`) rather than only the two config hashes, which name the writers but say nothing an operator can act on. The option is inert under ackMode: 'none', where the server tracks no acknowledgements and there is nothing to time out, and the in-memory, Redis and core-NATS adapters ignore it, having no server-side acknowledgement window at all. Keep it above the slowest run of the handler: a window that expires while the handler is still working redelivers the message and does the work twice. The shutdown drain remains a fixed 30 seconds, so a handler granted a longer `ackTimeout` can still be abandoned by a deploy (`@onebun/core`, `@onebun/nats`)

### Bug Fixes

- **WebSocket gateways can authenticate a client, so `WsAuthGuard` can pass at all** — the framework parsed the bearer token and then created every client with `authenticated: false`, and nothing anywhere set it to `true`: `grep -rn 'authenticated' packages/core/src/websocket/*.ts` found exactly one assignment, that one. So `WsAuthGuard` — exported, documented, and shown in the guards example — denied every client forever, and `WsPermissionGuard` checked a permission list nobody populated. A handler guarded with either was unreachable. `@WebSocketGateway({ authenticate })` now runs during the upgrade with three outcomes: `false` refuses it with HTTP 401, `null` admits the client as ANONYMOUS so authentication guards still deny it, and `true` or an object admits it as authenticated with the identity the guards read. Omitting the option keeps the previous behaviour. It surfaced while fixing the decorator-order bypass: the framework's own integration test named `should allow protected handler with valid auth token` passed only because the guard was never running (`@onebun/core`)
- **`DrizzleService` and `CacheService` close their connections on shutdown** — both had a `close()` method and nothing in the lifecycle ever called it, so a service built by one test suite kept its connection open into the next. That is the direct mechanism behind a suite failing with `database "..." does not exist` after an earlier suite dropped its throwaway database. Both now implement `OnModuleDestroy` and close on `app.stop()`. A SHARED Redis client is deliberately left alone by the cache hook: `close()` disconnects only a client the service owns, and the application already disconnects a shared one during `stop()`, gated on `closeSharedRedis`, so `stop({ closeSharedRedis: false })` keeps it connected for the rest of the process (`@onebun/drizzle`, `@onebun/cache`)
- **`@Global()` modules are constructed before ordinary imports** — the application now walks the static import graph from the root, finds every reachable `@Global()` module and builds those first; the rest of the tree follows as before. This is what makes import order irrelevant in both directions rather than only one. Two visible consequences beyond that: a global module's providers are constructed earlier relative to non-global ones, so `onModuleInit` on a global service runs before that of a service in a module declared ahead of it; and a global module appears first among its parent's child modules, which affects only code reaching into `childModules` directly (`@onebun/core`)
- **The documented multi-database and multi-cache pattern never worked, and the documentation is corrected** — `docs/api/drizzle.md` and `docs/api/cache.md` presented two `forRoot()` calls as the way to run a main and an analytics database. `forRoot()` stores its options on the module CLASS, which the whole process shares, and `DrizzleService` reads them late at `onModuleInit` — so both calls settle before either service reads, and every instance connects to whichever was evaluated LAST. Reproduced from the published example verbatim: two distinct `DrizzleService` instances, both on `main.db`, no error, nothing in the logs. Anyone who followed it sent every analytics write into their production database. Both pages now state what actually holds — `isGlobal: false` gives each importing module its own INSTANCE, all instances share ONE configuration, `forFeature()` constructs a new instance rather than handing back the root's, and the boundary is the PROCESS, so a second application does not help either. They also point at what DOES work today: `new DrizzleService()` plus `initialize(connection)` reaches a second, independently configured database, and a `@Global()` module re-exporting the service shares one instance without making the module itself global. **If you followed the documented pattern, audit BOTH databases**: all the writes are in one of them, and which one depends on module evaluation order rather than on the order you declared them (`@onebun/drizzle`, `@onebun/cache`)
- **⚠️ A nacked message is reported as failed, not processed, on every adapter** — the documented way to write a handler is a `try`/`catch` whose `catch` calls `message.nack()`. Such a handler never throws, so nothing about its control flow distinguished it from a success: every adapter emitted `onMessageProcessed` for a message it had just dropped or requeued, and `onMessageFailed` fired only when a handler let an exception escape. A service written exactly as the documentation recommends therefore reported a failure rate of structurally zero while losing or retrying messages, and a message that took five attempts counted as five successes. Each adapter now reads the nack the message already recorded and emits `onMessageFailed` with a synthesised error naming it. The flag is read through an adapter-internal accessor (`NackAwareMessage` and `wasNacked()` in `@onebun/core`), so the public `Message` interface is unchanged and handlers cannot read it back. A handler that nacks and then throws still emits exactly one event, carrying the thrown error rather than the synthesised one, and `ack()`/`nack()` are first-call-wins everywhere. The rule does not vary with `ackMode`: `'none'` removes redelivery, not observability. **Migration:** anything counting `onMessageProcessed` as throughput, or alerting on `onMessageFailed`, will see both numbers move on upgrade — the processed count falls by exactly the messages the handlers were already rejecting and the failure count rises by the same amount, so re-baseline the alert rather than treating the step as an incident. Check too that an `@OnMessageFailed` handler tolerates an error it did not raise: the handler never threw, so the `Error` it receives is the framework's (`@onebun/core`, `@onebun/nats`)
- **⚠️ `nack(true)` under `ackMode: 'auto'` on JetStream actually redelivers now** — the consume loop's auto-acknowledgement ran on the raw JetStream message rather than through the framework's wrapper, so it bypassed the wrapper's own first-call-wins guard. A handler that called `message.nack(true)` sent `nak()`, returned, and then had `ack()` sent on the same message microseconds later, settling it and cancelling the redelivery it had just requested; `nack(false)` was terminated and then acked in the same way. Manual redelivery was therefore silently inoperative in the one mode where the framework acknowledges for you — the call succeeded, the server was told twice, and the last word won. The auto-acknowledgement is now skipped for a message the handler already dispositioned. `ackMode: 'manual'` was never affected, because it sends no automatic acknowledgement at all. **Migration:** a handler that has been calling `nack(true)` under `ackMode: 'auto'` starts genuinely redelivering, up to `max_deliver`; if it was relying on the message quietly going away, give it a `deadLetter` queue or switch the call to `nack(false)` (`@onebun/nats`)
- **`@Subscribe` patterns with named parameters now reach NATS as valid subjects** — `@Subscribe('orders.{id}')` created a consumer filtering the literal subject `orders.{id}`, which matches nothing on the broker. Nothing errored: `consumers.add` succeeded, `isConnected()` reported healthy, and the subscription was simply, silently dead. A single translation now runs at every point where a OneBun pattern reaches the wire — the consumer filter, the publish subject, stream declarations and stream resolution: a `{name}` parameter becomes the NATS `*` wildcard, a trailing `#` becomes `>`, and `*` and literal tokens pass through. Translation only ever widens, and the in-process matcher built from the original pattern still narrows the delivery back and rejects anything the pattern does not match, so a subscription never receives more than it asked for. A stream declared as `orders.{id}` binds `orders.*`; publishing is unaffected — `publish('orders.123', …)` still sends `orders.123` (`@onebun/nats`)
- **`Message.attempt` and `Message.maxAttempts` are populated on JetStream** — both fields were declared on the message and never assigned, so they were permanently `undefined`. That made the retry recipe the documentation ships dead code: `if (message.attempt && message.attempt >= (message.maxAttempts || 3))` could never be true, so every failure fell through to `nack(true)` and kept being redelivered until `max_deliver` ran out — the documented terminal branch was unreachable. `attempt` now comes from the delivery count the server already tracks (1-based, so the documented comparison works as written), and `maxAttempts` is the `max_deliver` the subscription's consumer was actually created with, resolved once at subscribe time rather than recomputed per message: with reconciliation the server-side consumer is authoritative, and re-deriving the precedence chain in the consume loop could disagree with the consumer that really exists. Under `ackMode: 'none'` the server tracks nothing, so `attempt` stays 1 by design. On the memory, Redis and core-NATS adapters both fields remain `undefined` for now (`@onebun/nats`)
- **Shutdown waits for handlers that are still running** — `unsubscribe()` and `disconnect()` abandoned any handler that was mid-flight. Its acknowledgement was then published onto a closing connection, where the client buffers it and drops it without raising anything: the handler completed, the server never heard about it, and the message was redelivered after `ackWait`. Since `QueueService.stop()` unsubscribes every subscription on graceful shutdown, that ran on every deploy — duplicating exactly the charge-and-email work the documentation recommends handlers for. Both calls now wait for the running handler, bounded by a fixed 30 seconds matching the default `ackWait`, and `disconnect()` stops each subscription pulling before it waits, so no new handler starts during the drain. Shutdown now takes as long as the slowest handler in flight, where it previously returned immediately (`@onebun/nats`)
- **The queue adapter is no longer connected twice on startup** — `QueueService.initialize()` called `connect()` unconditionally on an adapter the application had already connected, so every boot opened the backend connection twice. It is now guarded by `isConnected()`, matching the guard `QueueService.start()` already applied to the same call (`@onebun/core`)
- **Publishing to an unbound subject reports the real cause** — JetStream stores a message only if some stream on the broker binds its subject, and the server's rejection for an unbound one is `jetstream is not enabled`, which names neither the subject nor the streams. The adapter now re-reports it with the OneBun pattern, the resolved NATS subject and every stream this application declares, keeping the broker's rejection as the error's `cause`. There is no pre-flight check against the local `streams` list — a subject may legitimately be bound by a stream another service owns (`@onebun/nats`)
- **A `@Global()` module reaches importers that were initialized around it** — module initialization read the global registry once, at the top, and then walked `imports`; an entry already initialized by an earlier sibling in the same array was skipped on the assumption that first pass had delivered it. It had not: the sibling registered it afterwards. So `imports: [FeatureModule, CoreModule]` — where `FeatureModule` also imports `CoreModule` — failed at boot with `Could not resolve dependency`, while `imports: [CoreModule, FeatureModule]` booted, a one-token difference between a module that works and one that cannot resolve its own declared import. The same defect hid a global module from an ancestor that did not list it directly. The registry is re-read after the import loop, and an import that re-seeds services from an already-initialized global module now logs a debug line naming both modules and the count — the silence is what made this expensive to find. The module is still constructed exactly once. Import order is now irrelevant for `@Global()` modules in both directions: every global module reachable from the root's import graph is constructed BEFORE the ordinary import loop runs, so a consumer nested inside a subtree built earlier in the same array resolves too — `imports: [FeatureModule, CacheModule.forRoot()]` with a service deep inside `FeatureModule` injecting `CacheService` used to fail at boot at any depth, and now behaves identically to `[CacheModule.forRoot(), FeatureModule]`. The walk reads metadata only, constructs no provider of its own, and a global module is still built exactly once (`@onebun/core`)
- **A NestJS-style object provider throws instead of vanishing** — `@Module({ providers: [{ provide: X, useValue: v }] })` typechecks against the metadata shape, but every filter downstream drops anything that is not a function, so the entry simply never existed. The failure then surfaced somewhere else entirely, as `Could not resolve dependency` on whichever service expected it. Such an entry now throws `OneBunInvalidProviderError` naming the module and the entry, and pointing at class-based providers and `TestingModule.overrideProvider()` (`@onebun/core`)
- **Lifecycle hooks on a `@Global()` service fire exactly once** — a global instance sits in the service map of every module that can see it, and the four lifecycle passes walked those maps and then recursed into child modules with no record of what they had already visited. `onApplicationInit`, `onModuleDestroy`, `beforeApplicationDestroy` and `onApplicationDestroy` therefore fired once per module — five times in a five-module tree — so a `close()` written in `onModuleDestroy` ran repeatedly against the same connection (`@onebun/core`)
- **By-class service lookups accept a service that has dependencies** — `app.getService()`, `CompiledTestingModule.get()`, `getServiceByClass()`, `getServiceTag()` and `createServiceLayer()` typed their parameter as a constructor taking `unknown[]`, which no class with typed constructor parameters satisfies. Passing any service with injected dependencies — that is, most of them — was a compile error even though the lookup worked perfectly at runtime (`@onebun/core`)

### Improvements

- **JetStream streams are reconciled through a configuration stamp** — OneBun stamps a hash of the applied stream configuration into stream metadata, so a stream that already matches is left untouched — no `streams.update` call at all — and a changed configuration is applied with every pre-existing metadata key carried forward. Two services writing different definitions for the same stream no longer overwrite each other: the second writer sees the hash it just applied already replaced and fails with a reconcile-cycle error naming the diverging fields. The stamp requires nats-server 2.10 or newer, and a rejection that names that requirement is re-reported with it stated (`@onebun/nats`)
- **`consumerConfig.maxAckPending` is honoured** — the option was declared but read nowhere, so anyone who set it silently got 100. Consumer wire values now come from a single resolver with a documented precedence: `max_ack_pending` takes `prefetch`, then `consumerConfig.maxAckPending`, then `100`; `max_deliver` takes `retry.attempts`, then `consumerConfig.maxDeliver`, then `3`; `ack_wait` takes `consumerConfig.ackWait`, then 30 seconds. The pull batch is `min(max_ack_pending, prefetch ?? 10)`, so a subscription can never request more messages than the server will let it hold unacknowledged (`@onebun/nats`)

### Breaking Changes

- **⚠️ Fail-fast dependency resolution** — unresolved DI dependencies now throw `DependencyResolutionError` at bootstrap instead of silently injecting `undefined`. Services, controllers, middleware, and interceptors with missing required dependencies will crash immediately with an actionable error message that names the missing dependency and suggests which module to import or export. Use the new `@Optional()` decorator to opt into the previous behavior for intentionally optional dependencies (`@onebun/core`)
- **⚠️ Circular dependencies throw** — circular dependency detection now throws `CircularDependencyError` instead of logging an error and continuing with broken wiring. The error includes the full dependency chain for debugging (`@onebun/core`)
- **⚠️ Missing controller metadata throws** — controllers listed in a module's `controllers` array without a `@Controller()` decorator now throw `OneBunBootstrapError` at startup instead of being silently skipped. WebSocket gateways (`@WebSocketGateway()`) are correctly excluded from this check (`@onebun/core`)

### Improvements

- **`DependencyResolutionError` with diagnostic suggestions** — when a dependency cannot be resolved, the error message searches all registered modules to find where the missing type is provided: suggests adding the module to imports, adding the type to exports, or notes when a global module should have auto-resolved it (`@onebun/core`)
- **`@Optional()` decorator** — marks constructor parameters as optional for DI. When the dependency cannot be resolved, `undefined` is injected instead of throwing. Works with services, controllers, middleware, and interceptors (`@onebun/core`)
- **Per-request trace context isolation** — HTTP request trace context is now stored in `AsyncLocalStorage` instead of `globalThis`, eliminating a race condition where concurrent requests could overwrite each other's trace IDs. Each request gets its own isolated trace context scope via `requestContextStore.run()` (`@onebun/core`)
- **`traceContextGetter` in logger** — `SyncLogger` and `LoggerImpl` now accept a `traceContextGetter` callback for reading per-request trace context from `AsyncLocalStorage`, replacing the `globalThis.__onebunCurrentTraceContext` fallback. The `globalThis.__onebunTraceService` fallback is preserved for non-HTTP contexts (WebSocket, queues) (`@onebun/logger`)
- **Bootstrap error propagation** — `OneBunBootstrapError` and its subclasses (`DependencyResolutionError`, `CircularDependencyError`) are now re-thrown from the service creation catch block instead of being swallowed (`@onebun/core`)

### New Exports

- `DependencyResolutionError`, `CircularDependencyError`, `OneBunBootstrapError` — bootstrap error classes (`@onebun/core`)
- `@Optional()`, `isOptionalParam()` — optional DI parameter decorator and checker (`@onebun/core`)
- `getRegisteredModules()` — iterator over all `@Module()`-registered modules and their metadata (`@onebun/core`)
- `requestContextStore`, `getCurrentTraceContext()`, `RequestContext` — per-request `AsyncLocalStorage` for trace context isolation (`@onebun/core`)
- `LoggerConfig.traceContextGetter` — optional callback for per-request trace context resolution (`@onebun/logger`)
